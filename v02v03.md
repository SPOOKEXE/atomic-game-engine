# v0.2 / v0.3 — plan

The Universe/World layer, engine-owned storage, multi-world and multi-process
execution, and the components and physics that sit on top of it.

Written before any code, because these two versions share one decision — *what
a world is allowed to touch* — and getting that wrong is not a refactor later,
it is a rewrite.

## The shape of the whole thing

Userland gets **Roblox-style instancing, tweaked**. Scripts see instances,
properties, a `Parent`, `GetChildren()`, `.Changed`, `:IsA()`, `:Destroy()`.
Under it there is no instance object at all: an instance is an entity, a class
is a set of components, a property is a column, and every system iterates rows.
**The engine is full ECS; the tree is a façade.**

That is not a decoration on this plan, it is the reason its central pieces look
the way they do:

| Userland concept | What it actually is | Where it comes from |
|---|---|---|
| `Instance` handle | `ecs::Entity` (index + generation) | exists |
| `ClassName`, `:IsA()` | an interned `ComponentSet` plus a class table | v0.2 storage |
| a property | a field in a `Column`, reached by `core::Name` | v0.2 storage |
| `.Changed` | `ChangeChannel`, fired at a phase boundary | v0.2 storage |
| `Parent` / `GetChildren()` | an intrusive sibling list, not a transform hierarchy | v0.2 |
| `workspace` | one world's root instance | v0.2 |
| `game` | the bus services, and nothing else shared | v0.2 |
| `MessagingService`, `DataStore`, `MemoryStore` | the only channels between worlds | v0.2 |
| `:GetAsync()` and friends | a `Ticket`; the reply lands next tick | v0.2 |
| `Part` | a class: `{Transform, Bounds, Visual, Collider, Surface}` | v0.3 |

## What this is planning against

Everything below is constrained by rules that already exist in `AGENTS.md` and
by numbers already measured. Restated because the plan is only correct in the
presence of them:

| Rule | Consequence |
|---|---|
| Nothing crossing a world boundary is a pointer | The message layer is bytes from day one — and in v0.2 some of those bytes really do cross a pipe |
| Work inside a tick may be parallel, work across ticks may not | Cross-world effects and `.Changed` signals land at a tick boundary, never mid-tick |
| A name crosses boundaries, a number does not | Worlds, buses, topics, classes, properties and components are addressed by `core::Name`; every id is process-local |
| The ECS owns the storage | `Universe` holds no world state of its own — what it holds is the bus backends |
| A rule the build does not check is documentation | Every invariant below names the test that enforces it |

Measured facts that shape the design:

- `EachParallel` is **slower than serial below ~60-80k rows** and tops out near
  3.5x. A universe of many small worlds should parallelise *across* worlds
  rather than inside them.
- `Jobs::For` admits **one batch process-wide** and nesting deadlocks. §2.5 is
  about that collision.

**Documents referenced but not present in this repo:** `repo_layout.md`,
`GARG_ECS_Layout.md`, `RENDER_PIPELINE.md`. Layer heights below are inferred
from what the `AGENTS.md` files say — `world` at L4 (`ecs/AGENTS.md`), `scene`
at L7 (`mono.client/AGENTS.md`), `graph` at L9 and `render`/`input` at L12
(`render/AGENTS.md`), bindings at L13. Check the proposed heights for `spatial`
and `physics` against §6 of the real document before committing them.

## Decisions taken

| # | Decision | Consequence |
|---|---|---|
| 1 | **Process-per-world is implemented in v0.2**, not deferred | Needs world serialisation, which needs #2. Buys crash isolation |
| 2 | **The full storage rewrite lands in v0.2** — `Column`, `ComponentSet`, `SparseSet`, `ChangeChannel` | flecs is removed. `Store::Native()` debt is paid off. The instance façade becomes possible |
| 3 | **Cylinder collision is exact and analytic**, per pair | Six hand-written narrow-phase pairs in v0.3 |
| 4 | **`spatial` is its own L6 module** | Render culling can link it without linking physics |
| 5 | **`Camera` is a component *and* `ActiveCamera` is a resource** | Matches the roadmap and the instance model: a camera is an instance, so it is a row |
| 6 | **Worlds never address each other. They use buses** — MessagingService, DataStore, MemoryStore, Teleport | Routing is hub-and-spoke, not a mesh. Cross-world entity references stop existing entirely (§2.7) |
| 7 | **Target scale is mixed**: one or two worlds at 50k-500k entities, plus tens to hundreds at 1-10k | Both execution modes are real, and the mode becomes a *per-host* property rather than a universe-wide one (§2.5) |
| 8 | **Determinism is same-binary**, not cross-machine | The sorted apply, stable iteration and serial solver stay. Cross-machine agreement is documented as not promised |
| 9 | **Record and replay ship** — a versioned format, a runner, and a CI job | Cheaper than it looks: crash recovery already needs snapshot plus retained input (§2.4) |
| 10 | **Several worlds per host, with per-world soft-fault quarantine** and an `Isolation` flag for worlds that need their own | Soft faults are isolated; hard faults take the host. Both are stated rather than blurred (§2.9) |
| 11 | **A class carries its defaults as a prototype row** | `Instance.new` is a column copy and `:Clone()` falls out of the same operation |
| 12 | **The world driver lives in `mono.engine`.** Both programs run worlds from it; the server has authority and the client simulates its own replica and syncs | Single-player runs both on one machine; a dedicated server runs the server half and clients connect. Implies replication (§2.12) |
| 13 | **Teleport moves a player identity plus a payload**, never an arbitrary subtree | No cross-world class-version negotiation and no reference fixup. The destination decides what a player looks like when it arrives |
| 14 | **`ChangeChannel` is per-row dirty bits, stored as a lazily-added column** | Rides the existing storage: snapshots, archetype filtering and contiguity come free |
| 15 | **A faulted world auto-restores, with a crash-loop cutoff** | Survives a transient script error; a world faulting every tick goes down and reports instead of burning the host |

Decisions 1 and 2 reinforce each other — processes need snapshots, snapshots
need storage the engine controls — and 6 pays for both: with no direct
world-to-world traffic, the process topology is a hub and spoke rather than a
mesh, and every ordering decision lands in one place. Together with the instance
model they still make v0.2 **the largest version in this roadmap by a wide
margin.** That is stated plainly rather than discovered in month three;
Sequencing orders it so each step lands building and passing.

# v0.2

## 2.1 The shape

```
Universe                       the driver process; the DataModel root
├─ Directory                   Name -> {WorldId, Host, Isolation} for every world in the run
├─ Buses                       `game`'s services. The ONLY shared state there is:
│  ├─ MessagingService         pub/sub topics
│  ├─ MemoryStore              ephemeral shared: hash map, sorted map, queue
│  ├─ DataStore                durable key/value, versioned, read-modify-write
│  └─ Teleport                 move a player and its payload to a named world
├─ Supervisor                  child hosts, heartbeats, quarantine, restart
├─ Recorder                    snapshot plus retained input, per world
└─ Hosts[]                     each owning some worlds. A World is:
   ├─ Store                    its entire simulation state, engine-owned
   ├─ Root         Entity      `workspace` for this world
   ├─ Scheduler                its systems
   ├─ FixedTimestep            its own rate — worlds need not agree
   ├─ Inbox / Outbox           bus traffic only, as bytes
   └─ WorldState               Active | Idle | Suspended | Faulted
```

Two types carry the cross-boundary idea, and the third one this plan used to
have is gone:

```cpp
// Process-local, dense, never serialised. The stable identity is the Name.
struct WorldId { uint32_t Index = INVALID; };

// What crosses. Bytes, because a world is usually in another process.
struct Envelope {
	core::Name Bus;        // "MessagingService", "DataStore"
	core::Name Key;        // topic or key within that bus
	core::Name From;       // the publishing world
	uint64_t Sequence;     // per-sender, monotonic — the determinism key
	std::vector<std::byte> Payload;
};
```

**There is no `Address`, because there is no cross-world entity reference.** A
world cannot name an instance in another world any more than a Roblox server can
name an instance on a different server, and that is the correct model rather than
a limitation: sending a player to another subarea means serialising what the
player *is* and putting it on the Teleport bus, not handing over a pointer with
extra steps. Rule 3 stops being a discipline anyone has to remember — the type
that would have violated it does not exist.

`Universe` hands out `WorldId` and bus handles. **It never hands out a
`Store &`.** With worlds in separate processes that is no longer a discipline
either, it is arithmetic — the store is not in this address space.

### Who runs what

All of it is `mono.engine`. `Universe`, `World`, the buses, the supervisor and
the host loop are engine code at L4, and neither program owns any of it —
`mono.client` and `mono.server` both *run* worlds out of the same driver. That
is the existing rule rather than a new one: `mono.engine` is libraries, never a
product.

| Deployment | What runs | Notes |
|---|---|---|
| Dedicated server | `mono.server` only, worlds across N hosts | Authoritative. Clients connect over the network |
| Client | `mono.client`, simulating a replica of the world it is in | Predicts locally, reconciles against the server |
| Single-player | both, on one machine | `mono.client/AGENTS.md` already describes this: the client links `Mono::server` and hosts one over a loopback transport, the one named `ALLOW_TIER_ESCAPE` |

**The server has authority; the client simulates its own copy and syncs.** The
consequences run through the rest of this plan:

- The client always renders a world it holds locally, because it simulates one.
  So multi-world rendering (§2.11) is about *compositing several views*, not
  about fetching a world it does not have.
- A replica accepts authoritative state, which is snapshot application — already
  built for §2.9's restart. One mechanism, a third user.
- **A client replica must not write to a bus.** DataStore, MemoryStore and
  Teleport are server-authority operations; a replica issuing one is a bug, and
  the bus handle a replica holds refuses at the call rather than at review time.
- This needs a replication layer, which the roadmap does not currently have
  anywhere. §2.12 is what v0.2 reserves for it.

## 2.2 The storage rewrite

flecs goes. What replaces it has to serve four consumers at once, which is what
makes the shape non-obvious:

1. systems iterating rows fast,
2. Luau reading and writing properties **by name at runtime**,
3. serialisation, for snapshots and process migration,
4. the v0.4 bindings manifest, generated from the same metadata.

### `TypeDescriptor` — the piece that makes the other three possible

```cpp
struct TypeDescriptor {
	core::Name Name;              // "Transform" — what crosses, per rule 4
	uint32_t Size, Alignment;
	void (*ConstructRange)(void *, size_t);
	void (*DestructRange)(void *, size_t);
	void (*CopyRange)(void *, const void *, size_t);
	void (*Write)(core::ByteWriter &, const void *, size_t);
	void (*Read)(core::ByteReader &, void *, size_t);
	std::span<const PropertyDescriptor> Properties;   // name, offset, value type
};
```

A component is no longer only a C++ type — it is a registered descriptor. That
single addition is what lets a column be serialised without knowing `T`, lets
Luau resolve `part.Size` to an offset, and gives the manifest generator
something to read. Registration happens once per process at startup, in a fixed
order, which also makes archetype ids deterministic (§2.4).

### The four names

| Type | Is | Serves |
|---|---|---|
| `Column` | one type-erased contiguous array + its descriptor + a version stamp | iteration, properties, serialisation |
| `ComponentSet` | an interned, immutable set of component ids | archetype identity **and** `ClassName` |
| `SparseSet` | entity index → `{archetype, row}`, plus the generation array | `Alive`, handle resolution, the hierarchy links |
| `ChangeChannel` | a column version, plus **per-row dirty bits held as a lazily-added column of their own** | `.Changed`, render cache invalidation, replication deltas |

### Dirty tracking is a column, not a side table — and never a tag

Storing the dirty bits *as component data* is the better version of the idea, and
it costs nothing extra: `DirtyBits { uint64_t Mask; }` sits in the archetype
beside the columns it describes, so snapshots carry it, iteration finds it
contiguous, and it is added only to the classes something actually observes. A
500k-entity world with ten tracked columns spends about 4 MB on it; a 10k world
spends 80 KB.

**The trap, stated because the idea invites it:** do not make "changed" a *tag*.
A tag is part of the `ComponentSet`, so adding one moves the row to another
archetype — a structural change on every property write, and archetype churn
every tick. A bitmask column is a plain write to memory the row already owns.
The difference between the two is the difference between free and unusable.

Batch writes through raw column pointers still set no bits — that gap is what
`QuickHash` covers in v0.3, and it should be labelled as the fallback it is.

Around them: an `Archetype` holds one `ComponentSet` and one `Column` per member
plus the entity id array; an archetype graph caches add-one/remove-one edges so
adding a component is a hop rather than a search; a `Query` is a cached list of
matching archetypes invalidated on archetype creation — which closes `D00003`
permanently rather than working around it.

### What the rewrite pays off

- `Store::Native()` disappears. `ecs/AGENTS.md` calls it a debt; this is the
  payment.
- `D00003` (a query built per `Each` call) is fixed by construction.
- `D00002`'s render graph gets `ChangeChannel` and node rows.
- `FLECS_MULTI_WORLD`, mid-tick auto-registration and flecs's global component
  index all stop being concerns.
- `mono.vendor/flecs` and its entries in both `THIRD_PARTY_NOTICES.md` files go.
  Delete the thing you replaced.

### What it costs

The measured `EachParallel` numbers were taken against flecs tables. They will
move, and the comments carrying them have to be re-measured rather than copied
forward. Expect the crossover to change; do not expect it to vanish.

## 2.3 The instance façade

Nothing in Luau exists yet — that is v0.5 — but the *data* it binds to is built
here, and building it later means rebuilding the storage.

**The first consumer is C++, and stays C++ through v0.3.** The test scene is not
being ported to script until v0.4's bindings manifest and v0.5's VM, so the class
table, the property descriptors and the hierarchy are reached from C++ first and
from Luau second. That is the right order rather than a compromise:

- The façade gets exercised by real code a whole version before a VM exists, so
  its mistakes surface while they are still cheap to fix.
- A C++ path that is *the same table* Luau will use — rather than a parallel
  convenience API that gets deprecated in v0.5 — is the only version worth
  building. Two ways to create an instance is the debt this repo warns about.
- If a class can only be built by writing a Luau string, the storage cannot be
  unit-tested without a VM. That alone settles it.

So `Instance.new("Part")` in v0.5 and `scene::Create(store, Classes::Part)` in
v0.3 resolve the same class id, land in the same archetype and copy the same
defaults. Luau adds a calling convention, not a mechanism.

**Class table.** A class is a name, a parent class, and a `ComponentSet`.
`:IsA()` is an ancestor test, made O(1) by interval-numbering the class tree at
registration. `Instance.new("Part")` is: look up the class, create an entity in
the archetype its set names, initialise from the class defaults.

**The hierarchy is not a transform hierarchy.** In Roblox `BasePart.CFrame` is
world-space and parenting is organisational. Keeping that is worth a great deal:
no propagation pass, no dirty-transform cascade, physics reads `Transform`
directly, and the tree costs four entity handles per node:

```cpp
struct Hierarchy { ecs::Entity Parent, FirstChild, NextSibling, PrevSibling; };
struct InstanceName { core::Name Value; };
```

Append at the tail so `GetChildren()` is insertion-ordered and therefore
deterministic — replication and replay both depend on that. `FindFirstChild` is
a walk of the sibling list; add a per-parent name index only when a measurement
says to, not before.

**Properties** resolve through the class table to `{component, offset, type}`.
Reads are a lookup and a load. Writes go through the store so the column version
advances — which is what makes `.Changed` possible without an observer per
property.

**Signals fire at a phase boundary**, not at the moment of assignment. Same rule
as messages, same reason: a callback running in the middle of a parallel batch
would make the tick stop being one thing that starts and finishes. A property
written three times in one tick signals once.

**Two deliberate tweaks away from Roblox**, both worth writing into
`world/AGENTS.md` so they read as decisions:

- **`:Destroy()` frees the row.** Roblox keeps a destroyed instance readable
  while a script holds a reference. Here the entity is destroyed and the handle
  becomes a tombstone that errors on access. Zombie rows in a column are a cost
  every iterating system pays forever.
- **There is no handle to an instance in another world.** Not a weak one, not an
  async one — the concept does not exist, exactly as it does not between two
  Roblox servers. Cross-world work goes on a bus (§2.7).

**Class defaults are a prototype row.** Each class owns one hidden row carrying
its defaults, so `Instance.new` is a column copy out of it and `:Clone()` is the
same copy from a different source row. No constructor callbacks: a function is
not something the bindings manifest can describe or a save file can contain, and
the prototype is just another row that snapshots already handle.

## 2.4 Determinism, recording and replay

### The guarantee

**Same binary, same machine, same result.** Cross-machine agreement is *not*
promised and must be documented as not promised: floating-point contraction and
`libm` differ between compilers and chips, and closing that gap means strict FP
flags and eventually fixed-point physics.

**This does not conflict with a client predicting and the server correcting**,
and the distinction is worth being precise about because it looks like it should:

- **Deterministic lockstep** — client and server run the same simulation from the
  same inputs and are expected to agree — *would* need cross-machine determinism,
  and is therefore not what this engine does.
- **State reconciliation** — the client predicts, the server sends authoritative
  state, the client corrects toward it — needs no agreement at all. A Windows
  client and a Linux server drifting apart is *expected*; correcting the drift is
  the whole mechanism.

So decision 8 stands and the authority model in §2.1 is compatible with it. What
same-binary determinism buys stays what it was: exact crash recovery, a working
parallel-equals-serial test, and reproducible bugs.

The archetype layer introduces a new way to lose even the same-binary guarantee,
and it is easy to miss: **iteration order follows archetype creation order.** Two
runs that create archetypes in a different order iterate rows in a different
order, and a floating-point sum diverges. Two things pin it — every component and
class is registered at startup in a fixed order, and archetypes are iterated by
interned set id. Nothing may create a component type at runtime; the registry
enforces that by refusing.

### The standing discipline

The real price of determinism is not the serial solver, it is a rule that binds
every system author from now on. **No simulation system may read wall-clock time,
a thread id, a pointer address, or iterate an unordered container.** Put it in
`ecs/AGENTS.md` next to the affinity rule, because it has the same shape: it is
invisible at the call site and expensive to find later.

### Recording is snapshot plus input

Shipping replay costs far less than it looks, because §2.9's crash recovery
already needs both halves. A world is deterministic given its state and its
inbox, so:

> **recording = one snapshot + every envelope delivered since, in delivery order**

There is nothing else to capture. A headless world has no other input, and the
inbox is already sorted deterministically before delivery, so a recording is a
faithful log rather than a reconstruction. The retention window the supervisor
already keeps for restart *is* the recording buffer.

The format is versioned and records component and class **names**, never ids, so
a rename or a reordered registration does not invalidate yesterday's recording —
rule 4 paying off a third time.

### What ships

- **`mono.server --replay <file>`.** A mode of the existing program rather than a
  new tool: it is already the headless driver, and a replay is just a driver
  whose bus deliveries come from a file instead of from live worlds.
- **A CI job** that runs a scene twice and diffs final state, so a determinism
  regression is caught the day it lands rather than the week a bug becomes
  unreproducible.
- **`--record <file>`** on the server, off by default.

Later, the client can replay for visual debugging; nothing here prevents it and
nothing here waits for it.

## 2.5 The `Jobs` collision, and the fix

`Jobs::For` keeps one `Batch` in a process-wide `Pool` and writes `pool.Current`
under the lock. Two threads calling `For` concurrently is not merely
"unsupported": the second overwrites `Current` while the first waits on an
`Outstanding` count that workers are decrementing for a different batch. Ticking
worlds in parallel puts every world's `EachParallel` in exactly that position.

**Resolution: worlds are the batch.** Ticking the local worlds *is* one
`Jobs::For` over the active list with `grain = 1`. No separate world threads: the
pool is sized once, the caller drains alongside it, and load balancing comes free
from `Next.fetch_add(1)` claiming worlds dynamically. Two changes make it safe:

1. **A nested or concurrent `For` runs inline.** Claim the pool with an atomic
   exchange at the top of `For`; a caller that loses the claim runs
   `body(0, count)` on its own thread. No deadlock, no work stealing, no flag.
2. **`Store::Owner` becomes atomic.** A world is picked up by whichever worker
   claims it, so `BindToCallingThread` runs every tick from a different thread.
   A plain `std::thread::id` written by one thread and read by another is a data
   race by the letter of the standard even where it is benign in practice.

(1) is honest rather than a fudge because of a property the code already has:
**the parallel iteration paths are observationally order-independent.** The body
writes only its own row, and the batch path hands out an absolute `first` index,
so running ranges on one thread or twenty produces the same bytes. Inline is a
timing change, not a result change. Say that in `parallel/AGENTS.md` — it is why
the whole scheme is allowed to exist.

The cost: while worlds tick in parallel, intra-world parallelism is gone. Given
the measured crossover that is right for many small worlds and wrong for one big
one — and the target scale is **both** (decision 7), so neither can be the only
mode:

| Mode | When | Behaviour |
|---|---|---|
| `WorldParallel` | a host holding many worlds, each below the crossover | one `For` over worlds, `EachParallel` inline |
| `WorldSerial` | a host holding one or a few large worlds | worlds tick in a loop, `EachParallel` uses the pool |

**The mode is a property of the host, not of the universe**, which is what makes
a mixed universe work rather than forcing a compromise: a large world takes
`Isolation::Dedicated` (§2.9) and its host runs `WorldSerial` with the whole pool
behind `EachParallel`; the hundreds of small worlds share hosts running
`WorldParallel`. The grouping decision and the execution mode turn out to be the
same decision, which is why the flag is worth having.

**The switch changes no result** — that is what makes it a tuning knob rather
than a semantic. Prove it with the test in §2.10, not with an argument.

One consequence to get right early: **each host sizes its own pool.** Every host
calling `Jobs::Start(0)` spawns `hardware_concurrency - 1` workers, so eight
hosts on a 24-core machine is a 190-thread oversubscription. Pools are sized from
a per-host budget the supervisor hands down.

## 2.6 The driver tick

```
Universe::Tick(frameSeconds)
  1. Drain control queue      create / destroy / suspend / quarantine worlds  [driver]
  2. Pump host channels       collect outbound envelopes from every host      [driver]
  3. Apply to buses           publishes, writes and reads, in sorted order    [driver]
  4. Fan out                  bus deliveries and replies into each inbox      [driver]
  5. Build the active list    worlds owing >= 1 tick, longest-first           [driver]
  6. Tick worlds              ----------------------------- PARALLEL ---------
  7. Fire deferred signals, collect timings, snapshot and record if due       [driver]
```

Only step 6 runs on more than one thread, and during it no world touches another
world and nothing touches a bus. Every cross-world effect is applied at the
barrier, on one thread, in a sorted order — which is where the whole determinism
story lives. It fits on one screen on purpose.

**Presentation is separate.** A client renders one world; the others still
simulate. `Universe::RunPresentation(WorldId, alpha)` runs `Phase::PreRender` for
one world on the driver thread after `Tick` returns — the existing client split
lifted one level.

**Per-world rates.** Each world owns a `FixedTimestep`. A world with no players
drops to `Idle` or `Suspended` (no ticks, no cost). Catch-up is already capped by
`MAXIMUM_TICKS_PER_FRAME`, so a stalled world falls behind and reports rather
than spiralling.

## 2.7 Buses — the only way anything crosses

**Worlds do not address each other.** There is no send-to-world, no world-to-world
route, and no reference to a foreign entity. Everything that crosses goes through
a named bus, and the buses are the Roblox ones:

| Bus | Shape | Used for |
|---|---|---|
| `MessagingService` | publish to a topic, subscribers receive | signalling, events, "a boss spawned in zone 4" |
| `MemoryStore` | ephemeral shared hash map, sorted map and queue | matchmaking queues, leaderboards, cross-world coordination |
| `DataStore` | durable key/value, versioned, read-modify-write | player data, inventories, anything that outlives the run |
| `Teleport` | move a **player identity plus a payload** to a named world | the only way anything "moves" between subareas |

This is not a restriction placed on top of the design — it *removes* pieces of
it. There is no routing table, no mesh of channels, no `Address`, and no question
of what happens when a world names one that has been destroyed. Naming a world at
all is reserved for the Teleport bus and for the supervisor.

**Teleport carries an identity and a payload, never an entity.** The destination
world rebuilds the character from its *own* class definitions, exactly as a
Roblox server does. That is what keeps two worlds from having to agree on class
versions, and it removes the question of what happens to a reference that pointed
outside the thing being moved — there is no thing being moved, only data
describing it. A world that wants a vehicle to survive a transition describes the
vehicle in the payload; it does not ship the instance.

### Hub and spoke

Because no world talks to another, every envelope goes host → driver → host. The
consequences are all good ones:

- **N channels, not N².** A host holds one channel to the driver regardless of
  how many worlds exist.
- **Ordering is decided in one place.** Step 3 applies every bus operation on the
  driver thread, so "what order did these two publishes happen in" has an answer
  by construction rather than by agreement between processes.
- **A world that goes down cannot corrupt a peer's view**, because it never had
  one. It published to a bus, and the bus is somewhere else.

### The rules that make it deterministic

- Every world has an **outbox** (written only by its own tick) and an **inbox**
  (read only by its own tick, at `PreSimulation`).
- Bus traffic issued during tick *T* is applied at the next barrier and delivered
  at the receiver's **next** tick. One tick of latency, always, regardless of
  thread or process scheduling.
- **Operations are applied in `(From, Sequence)` order.** Each sender's queue is
  already ordered by `Sequence`, so this is a **k-way merge, not a sort**. Without
  it, two worlds publishing in the same tick land in whatever order they finished
  in and a replay diverges — the detail easiest to skip and most expensive to
  find later.
- Worlds at different rates: "next tick" is the *receiver's*. A 10 Hz world
  subscribed to a 60 Hz publisher gets up to six at once, in order. No special
  case.

### Everything is asynchronous, which Roblox already taught everyone

Every bus call returns a `Ticket` and the reply lands in the inbox at a later
tick. That is not an engine limitation dressed up — it is the same contract as
`:GetAsync()`, so the semantics a Luau author already expects in v0.5 are the
semantics the engine wants anyway. A world tick occupies a pool worker, so
blocking one stalls the whole host batch; the async-only rule and the Roblox API
shape want exactly the same thing.

**Budgets** come with the model: each bus gives a world a request allowance per
tick, and over-budget calls fail with a named error rather than starving a
neighbour. Roblox has these because they turned out to be necessary; there is no
reason to rediscover that.

Payloads are trivially copyable structs written through `core::ByteWriter`, or
nothing at all for a bare signal. A `static_assert` at registration makes the
pointer rule checkable rather than remembered.

## 2.8 Universe data is the bus backends

The roadmap asks for "shared data in Universe" with "a lock mechanism for global
stores like player data". With buses, that resolves into something more concrete
than a shared store and a lock: **the Universe's shared data is the backing state
of the four buses, and nothing else.**

- `MemoryStore` — hash maps, sorted maps and queues, in the driver process.
- `DataStore` — a versioned key/value table with a durable backing. v0.2 ships the
  interface, the versioning and the read-modify-write conflict retry over an
  in-memory table; the durable backing lands with v0.7's filesystem work. Say
  which half is real, so nobody ships a save on top of a hash map.
- `MessagingService` — topic subscription tables, no retained state.
- `Teleport` — an in-flight payload table keyed by ticket.

There is **no general-purpose shared `ecs::Store`.** Player data is a DataStore
key, not a row in a world nobody owns. That removes a whole class of question:
who ticks it, which thread owns it, what happens when it is in another process.

Why no lock on the simulation path: the lock is what everyone reaches for and it
is what makes replay impossible — two worlds taking a write lock in whatever
order they reached it is nondeterminism written into the core of the simulation.
There is a concrete obstacle too: `Store` aborts on cross-thread access in every
build, and with worlds in separate processes there is no shared address space to
lock anyway. Step 3 applies bus operations one at a time on one thread, so the
serialisation a lock would provide is already there — and it is *ordered*, which
a lock never is.

**The escape hatch survives, narrowed.** `Universe::Exclusive<T>()` is a scoped
`std::shared_mutex` guard over a bus backend, for consumers genuinely outside the
simulation: persistence flushing, an admin console, a stats scrape. Rules, in
`world/AGENTS.md`:

- A `System` may never take it. Systems reach a bus through a `Ticket`.
- Anything read through it is non-replayable by definition, so nothing the
  simulation depends on may live behind it.

## 2.9 Processes, hosts, and two kinds of failure

In scope for v0.2. The argument is **crash isolation**, not speed. Say that in
the module docs, because "processes are faster" is the usual reason given and it
is usually false.

```
mono.server (driver)                        mono.server --host (child)
  Universe: buses, directory, recorder        several worlds, one pool, one mode
  Supervisor: spawn, heartbeat, quarantine    Store, Scheduler, FixedTimestep each
  one ipc::Channel per host                   one ipc::Channel to the driver
```

A host is not a new program: it is `mono.server` started in host mode, which is
what makes the grouping a deployment decision rather than an engine one.

### Several worlds per host, and per-world isolation that is honest

A host owns several worlds. Whether a neighbour's failure takes yours down
depends on which *kind* of failure it was, and blurring these two would be the
dishonest move:

| | Examples | Blast radius | Recovery |
|---|---|---|---|
| **Soft fault** | a system throws, a Luau script errors (the dominant mode once v0.5 lands), a tick budget overrun, a failed game-logic assertion | **one world** | mark `Faulted`, restore from snapshot or suspend; neighbours never notice |
| **Hard fault** | `abort()` from the affinity check, segfault, OOM | **the whole host** | supervisor respawns, restores every world in it from snapshot |

Soft faults are caught at the world-tick boundary, which is a place that already
exists — a world tick is one call in the `Jobs` batch, so wrapping it is free.
That is real per-world isolation inside a shared process and it covers the
failures that actually happen in a scripted game.

Hard faults cannot be isolated in-process and it would be wrong to claim
otherwise. Catching `SIGSEGV` and continuing means continuing with a heap that
may be corrupt, which makes the *neighbours* suspect too. The affinity check must
keep aborting for the reason `ecs/AGENTS.md` already gives: by the time it fires
the race has happened, and unwinding hands corrupted state to whoever catches.

**So a world declares what it needs:**

```cpp
enum class Isolation { Shared, Dedicated };   // default Shared
```

`Dedicated` buys protection from a neighbour's hard fault and nothing else — soft
faults are quarantined either way. It costs a process, a pool and an address
space, so it is for the handful of worlds that warrant it: the persistent
overworld, anything running untrusted content. It also happens to be the flag
that selects `WorldSerial` (§2.5), because a dedicated host holds one world.

### Recovery: automatic, with a cutoff

A `Faulted` world restores from its last snapshot and resumes. **After N faults
inside a window it stays down and reports**, because the failure that matters is
not the transient script error — it is the world that faults deterministically
every tick, restoring and re-faulting forever while consuming the host's budget.
Without the cutoff that world looks alive on every dashboard.

Both numbers go on F5 and in the server summary: faults per world, and worlds
currently held down. A fault that nobody can see is the same as a fault that was
swallowed.

### The rest of the machinery

- **`parallel/process/`** — spawn, supervise, heartbeat, terminate. Sub-area
  already reserved by `parallel/AGENTS.md`.
- **`parallel/ipc/`** — `Channel`, a framed byte queue, plus `SharedRegion` for
  bulk payloads. Two implementations from the start: local and pipe/socket. The
  caller never learns which it has.
- **Snapshots.** A world serialises through the `TypeDescriptor`s: the component
  registry as names, each archetype as a name set, each column as bytes, the
  entity array and generations, the hierarchy. Names on the wire, ids local.
  Taken every N ticks at step 7.
- **Restart.** On a missed heartbeat or a hard fault the supervisor respawns the
  host, restores each world's last snapshot, and replays retained inbox traffic
  from that tick. This is exactly the recording of §2.4 — one mechanism, two
  users.
- **Migration** is snapshot plus directory update plus in-flight forwarding.
  Falls out of the above; ship it if it is cheap, defer it if not.

Drawing a world that a child host owns is §2.11, and it is in scope for v0.2.

## 2.10 Tests — invariants, not API

- **Parallel equals serial.** Tick N worlds in `WorldParallel`, tick an identical
  universe in `WorldSerial`, compare every column byte-for-byte. One test covers
  the `Jobs` claim, affinity rebinding and the inbox sort at once.
- **Snapshot round-trips.** Serialise a world, restore it into a fresh store,
  compare byte-for-byte. Then: tick both for 100 ticks and compare again — the
  second half is what catches a descriptor that saves state but not identity.
- **A killed host is restored transparently.** Kill a child mid-tick; the world
  resumes from its snapshot with the same tick number and the same state a
  never-killed run had at that tick.
- **Delivery latency is exactly one tick**, with 0 workers and with many, local
  and across a channel.
- **Bus apply order is `(From, Sequence)`** with publishers finishing in a
  hostile order, and identical whether they were in one process or four.
- **A soft fault quarantines one world.** Throw from a system in a host holding
  eight worlds; that world goes `Faulted` and the other seven tick on with state
  identical to a run where the throw never happened.
- **A recording replays to the same final state**, and a recording made before a
  component was renamed still replays after — the name-not-id guarantee.
- **Nested `For` does not deadlock** and matches the unnested result.
- **Archetype iteration order is stable** across two runs that build the world in
  a different order.
- **`Universe` exposes no `Store &`**, and no type in `world/include` pairs a
  world name with an entity — the negative tests worth having.
- **Suspended worlds cost nothing**: no tick advance, no systems run.
- **The class table**: `:IsA()` across the tree, `Instance.new` lands in the right
  archetype and copies the prototype row, `:Clone()` matches a fresh construct
  plus assignment, `Destroy` frees the row, `GetChildren` is insertion-ordered.
- **A bus over budget fails by name** rather than starving a neighbour.

## 2.11 Multi-world rendering

Built now rather than at v0.6, because **one mechanism serves several consumers
already on the roadmap**: a surface camera for mirrors (v0.5), split-screen
across two worlds (v0.6), and any view whose producer is not the compositor. All
are the same thing — a *view* of a world, produced somewhere, buffered, and
composited by the client at its own frame rate.

One correction to what this section used to claim. With decision 12, **a client
simulates a replica of the world it is in**, so it renders a world it holds
locally and does not need a draw list shipped from a server. The cross-process
path therefore stops being the headline justification and becomes the general
case the design happens to cover: today's real consumers are mirrors and
split-screen, both in-process. That is still worth building now — two consumers
in the next two versions — but the argument is compositing, not remoting, and
saying otherwise would oversell it.

### The buffer, and why the lock goes

The shape is the buffered image you described. The change is the synchronisation:

**Three slots and one atomic publish index, not a lock.** The producer writes the
slot nobody holds and publishes by exchanging the index; the consumer takes the
index and reads. A lock is correct but couples the two rates — a compositor that
stalls a producer is a client stalling a simulation, and that is the one thing
the frame budget cannot absorb. With a triple buffer, a slow consumer **drops
frames instead of throttling the world**, which is the behaviour you want and
also what makes the remote case behave the same as the local one. The atomic
lives inside the shared region, so the identical code works across a process
boundary — `std::atomic<uint32_t>` is lock-free and needs no named mutex.

No backpressure and no queue: the consumer always takes the newest frame. Count
the dropped ones and put the counter on F5, so a starved view is visible rather
than mysterious.

### What is in the buffer: a draw list, not pixels

Two findings settle this, and both were checked rather than assumed:

1. **`mono.server` contains no renderer at all** — not "does not start one".
   That is enforced by the architecture test and by
   `just check-server-is-headless`, and `expected_graph.json` calls the server's
   row the load-bearing one. A host that publishes *pixels* needs a GPU device,
   which makes it a `client`-tier process. Publishing a *draw list* keeps hosts
   `server`-tier and the invariant intact.
2. **SDL3's GPU API exposes no external memory or shared texture handles.**
   Checked in `mono.vendor/sdl/include/SDL3/SDL_gpu.h`: there is
   `SDL_DownloadFromGPUTexture` for readback and nothing for exporting a
   texture to another process. So cross-process pixels mean GPU → CPU → shared
   memory → CPU → GPU every frame, with a readback stall at one end and an
   upload at the other. Roughly 8 MB per 1080p RGBA frame against roughly
   256 KB for 4096 draw instances.

The draw list also already exists as world state, produced at `PreRender`, and
`mono.client/AGENTS.md` names it as exactly the thing a second world would want
its own of. The renderer already issues one instanced call for the whole scene,
so two lists is two batches rather than a new pipeline.

**Pixels stay a payload variant, not a rejected idea.** The seam is the same
either way — a view publishes a framed payload — so the day a world is too
expensive to re-batch, or lives on another machine, an image variant is added
beside the draw-list one without disturbing the transport. Do not build it until
that case is real.

### Where it sits

```
World (any tier)      -- PreRender system packs a draw list -->  ViewChannel  (world, L4)
ViewChannel                                                       framed bytes, triple-buffered
Client (L12)          -- unpacks, interpolates by Alpha, composites N views into the swapchain
```

`world` at L4 carries the payload as **opaque bytes**, exactly as it does for
`Envelope`. It does not know what a draw instance is, and the tier check keeps it
that way for free. The layers above give the bytes meaning:

```cpp
// world, L4 — the transport. Presentation only: nothing here is read by
// simulation, so none of it has to be deterministic.
struct ViewHeader {
	core::Name World;
	uint64_t SourceTick;    // the tick that produced it
	float Alpha;            // the interpolation the producer used
	core::CFrame Camera;
	uint32_t Serial;        // monotonic; a consumer skips a repeat
	uint32_t PayloadBytes;
};
```

**One consequence for v0.3:** the draw-instance layout has to be a `shared`-tier
type, because a `server`-tier host writes it and a `client`-tier consumer reads
it. `render::Instance` is L12 and client-tier, so it cannot be the one. It
becomes `scene::DrawInstance` at L7 — `{CFrame, mesh Name, material Name, tint}`,
which is scene data rather than device data — and `render` converts it to
whatever the GPU wants. `mono.server` gains `scene` and `world` in its link row.

That sequences cleanly: **v0.2 builds and tests the transport with a synthetic
payload**, v0.3 gives it a real one with `scene::DrawInstance`, v0.5 consumes it
for the surface camera, v0.6 for split-screen.

### Timing

A view is published by a `PreRender` system on the producing world — which is
what `Scheduler`'s own comment already anticipates when it says `PreRender` on a
headless server is where replication will hang. It runs once per *host tick*, not
per client frame. The client composites at its own rate and interpolates using
the frame's `Alpha` and `SourceTick`, so staleness is at most one host tick.
v0.5's surface camera already accepts "use the previous frame as visual", so this
is the latency that design assumed.

### Rules

- **Nothing writes a `ViewFrame` into a store, and no simulation system reads
  one.** Views are presentation; letting one back into the tick would make the
  simulation depend on the frame rate of whoever was watching.
- A view is named by its world's `core::Name`, not by a `WorldId`, because it
  crosses.
- The in-process path and the cross-process path are the same call site with a
  different region. If they diverge, one of them is wrong.

### Tests

- **A view survives the producer running faster than the consumer** and vice
  versa: no tearing, no stall, `Serial` never goes backwards, drops are counted.
- **In-process and cross-process publish are byte-identical** for the same
  synthetic payload.
- **A killed host stops publishing and the compositor keeps running**, showing
  the last frame, and picks up cleanly when the supervisor restarts it. This is
  the one that catches a compositor holding a slot across a restart.

## 2.12 Replication — the seam, not the layer

Decision 12 says the server has authority and the client simulates its own
replica and syncs. **That is a replication layer, and the roadmap does not have
one anywhere** — v0.6 is rendering, v0.7 assets, v0.8 controls, and v0.9 onward
is unwritten. This is flagged rather than quietly absorbed, because it is a
subsystem on the scale of the storage rewrite, not a detail.

What v0.2 should do about it is **reserve the seam and build nothing else**:

- **`ChangeChannel`'s per-row dirty bits are the delta source.** Already being
  built for `.Changed` and render invalidation; a replication pass is a third
  reader of the same bits. Nothing extra is needed now beyond not designing them
  in a way only the renderer can use.
- **Snapshot application is state reconciliation.** Already built for restart
  (§2.9). A replica receiving authoritative state is the same operation against
  a live store instead of a fresh one — which is the one capability worth
  checking now, because "restore into a *running* world" is a harder shape than
  "restore into an empty one" and is cheap to allow for and expensive to retrofit.
- **A replica's bus handle refuses writes.** One flag on the handle, decided now,
  so no system is ever written assuming it can write to a DataStore from a
  client.
- **`PreviousTransform` and the interpolation `Alpha`** already exist for
  rendering and are what a corrected replica smooths against.

Everything else — a wire protocol, interest management, delta encoding, lag
compensation, client input submission — is a later version with its own plan. It
should not be started inside v0.2, and v0.2 should not ship anything that makes
it harder.

## 3.1 Where the components live

Not in `ecs` — that layer is storage and must not know what a `Transform` is.
Not in `mono.client` — `mono.client/AGENTS.md` already says the shared component
set becomes **`mono.engine/scene/` at L7 [shared]**, and that

| Module | Height | Tier | Deps |
|---|---|---|---|
| `mono.engine/scene/` | L7 | shared | core, ecs |
| `mono.engine/spatial/` | L6 | shared | core |
| `mono.engine/physics/` | L8 | shared | core, parallel, ecs, spatial, scene |

`spatial` is its own module because render culling wants the same structure and

**Delete the duplicated components, keep the C++ scene.** `Demo.hpp`'s

Two consequences worth stating:

- **The test scene is the acceptance test for the class table.** If building the

## 3.2 The components

```cpp
struct Transform         { core::CFrame Frame; };      // WORLD space, per §2.3
struct PreviousTransform { core::CFrame Frame; };      // render interpolation by Alpha
struct Bounds            { core::Vector3 HalfExtent; };
struct Motion            { core::Vector3 Linear, Angular; };
struct RigidBody         { BodyKind Kind; float Mass, LinearDamping, AngularDamping; bool Sleeping; };
struct Collider          { ShapeKind Shape; core::Vector3 Extent; uint32_t Layer, Mask; bool Trigger; };
struct Surface           { core::Name Material; };     // indexes a SurfaceTable resource
struct Visual            { core::Name Mesh, Material; core::Color3 Tint; bool Visible; };
struct Camera            { float FieldOfView, Near, Far; };
struct QuickHash         { uint64_t Value; };
```

The decisions inside that list:

- **`Motion` and `RigidBody` are split.** `Motion` is velocity, and anything with
  a `Transform` and a `Motion` moves — a platform, a projectile, the existing
  server demo. `RigidBody` adds mass and damping and makes it dynamic. So
  `Integrate` runs over `<Transform, const Motion>` and never loads a mass it
  does not use — the same reasoning that took `HalfExtent` out of the rows.
- **`Surface` is a `Name`, not coefficients.** Friction and restitution are the
  same two floats on thousands of entities: the resource case from
  `ecs/AGENTS.md` almost word for word. It names a row in a `SurfaceTable`
  resource that the narrow phase reads once.
- **`Bounds` is local half-extent**, the single source both the broad phase and
  render culling derive a world AABB from.
- **`Camera` is a component and `ActiveCamera` is a resource.** Under the
  instance model a camera is an instance, so it is a row — and a world can hold
  several (spectator, cutscene, security monitor). The resource names the live
  one and caches its resolved matrices, so "where is the camera" stays a lookup.
- **`QuickHash` is a fallback and must be labelled as one.** With `ChangeChannel`
  in v0.2, column versions cover most change detection. The gap is writes through
  raw column pointers in the batch path, which advance no per-row stamp.
  `QuickHash` is a content hash recomputed at `PostSimulation` for consumers that
  cannot observe. Write down that it is second-best, or it will spread.

## 3.3 `Part`

Not a component — a **class**, in the §2.3 sense: the name `"Part"`, a parent
class, and the `ComponentSet` `{Transform, Bounds, Visual, Collider, Surface}`.
`Instance.new("Part")` in v0.5 and `MakePart` in C++ are the same operation
through the same table.

```cpp
struct PartDesc { core::CFrame Frame; core::Vector3 Size; ShapeKind Shape;
                  core::Name Material, Mesh; bool Anchored; };
ecs::Entity MakePart(ecs::Store &store, const PartDesc &desc);
```

One place decides what a part is, so the editor, the loader, the bindings and the
tests cannot disagree. `Anchored` decides whether `RigidBody` and `Motion` are
present at all — which keeps static geometry in a different archetype rather than
skipped per tick.

## 3.4 `core/types` additions

`D00001` says the remaining value types arrive here "where they have a consumer".
The ones with a consumer in v0.3: `AABB` (broad phase, culling, world-space
`Bounds`), `Ray` and `RayHit` (the query API), and `Vector2` only if the overlay
or editor needs it. Nothing else — a value type without a caller is a maintenance
cost with no offsetting benefit, and `CFrame` already carries rotation.

## 3.5 The physics pipeline

Per world, inside that world's tick, entirely within its own store. Worlds never
collide with each other — a portal is a message, not a contact — so physics
parallelises across worlds for free and needs no concurrency story of its own.

| Step | Phase | Notes |
|---|---|---|
| `IntegrateMotion` | Simulation | `<Transform, const Motion>`, parallel. The shape already measured at 3.5x |
| `SyncBroadphase` | Simulation | world AABB from `Transform` + `Bounds` into the index |
| `BroadPhase` | PostSimulation | candidate pairs, **sorted by `(min id, max id)`** |
| `NarrowPhase` | PostSimulation | six shape pairs, producing contact manifolds |
| `Solve` | PostSimulation | sequential impulse, fixed iteration count, serial |
| `Publish` | PostSimulation | write back velocities, emit contact events |

**The index** is a uniform hash grid, cell size around twice the median collider
extent. A world is a bounded subarea by definition, which is the case a grid
handles better than a BVH: no rebuild, O(1) move, query is a cell walk. Revisit
only if collider sizes turn out wildly non-uniform.

**The six pairs** are exact and analytic (decision 3): box-box, box-sphere,
box-cylinder, sphere-sphere, sphere-cylinder, cylinder-cylinder. Box-box needs
SAT with clipped multi-point manifolds regardless — a single-point manifold
cannot hold a resting box still — so the cylinder cases are additions to that
machinery rather than a second approach. **Cylinder-cylinder is the one that goes
subtly wrong**: the disc-edge case and the parallel-axis degenerate case both
need explicit handling and explicit tests. Budget for it; do not discover it.

**Determinism.** Same binary, same platform, same result — which needs stable
iteration order (hence the pair sort and §2.4) and a **serial solver**. A
parallel sequential-impulse solver visits contacts in a nondeterministic order
and gives a different answer every run. Cross-platform determinism is not
promised and should be documented as not promised.

**Queries** are what game code actually uses: `Raycast`, `OverlapBox`,
`OverlapSphere`, `ShapeCast`, each with a layer mask. Per `parallel/AGENTS.md` a
system that raycasts per entity wants a grain in the tens — the default of 4096
is a guess about cheap bodies and a raycast is not one.

## 3.6 Measurement

Measured by **running the client and reading F3 and F5**, in the `release`
preset. Numbers worth having in comments by the end of v0.3:

- the serial/parallel crossover for `IntegrateMotion` on the new storage,
  carrying a `CFrame` rather than a `Vector3` — the old number does not carry
  forward across the rewrite;
- broad-phase cost per 1000 colliders, and how it moves with cell size;
- driver tick cost at 1, 4 and 16 worlds, in-process and hosted — the number that
  says whether the world-batch tail justifies work stealing;
- solver cost per contact, which decides the iteration count.

## 3.7 Tests

One suite per public header, per the existing convention. The behavioural ones:

- **A dropped box comes to rest** and stays at rest — the sleeping path, and what
  catches jitter at a resting contact.
- **A cylinder rests on its flat end** without wobble or drift, and on its side
  without sinking — the two cases the exact narrow phase was chosen for.
- **Two runs of the same scene agree byte-for-byte**, and agree at 30 Hz and
  240 Hz driver rates.
- **A raycast against a rotated box** — where a wrong inverse transform passes
  every axis-aligned test.
- **`MakePart` with `Anchored` adds no `Motion`** — keeps static geometry out of
  the dynamic archetype.
- **Physics in two worlds ticked in parallel equals two ticked serially.**

# Allocation, algorithms and async

A standing discipline for both versions, not a step. Three rules, in priority
order:

1. **Preallocate and reuse by default.** A buffer that is cleared rather than
   freed is the boring option and this codebase already prefers it — `DrawList`
   says so in its own comment: the capacity survives from frame to frame, so a
   steady scene stops allocating after the first one. Extend that everywhere the
   lifetime is known, which after v0.2 is almost everywhere.
2. **An algorithmic change needs a measurement, a data-structure default does
   not.** Swap-and-pop instead of shifting, a free list instead of `new`, a
   cached query instead of a rebuilt one — those are defaults, adopt them
   without ceremony. Replacing a grid with a BVH is a change with a number
   attached, taken in `release` and written into a comment.
3. **Async only off the tick's critical path.** Rule 5 stands: work across ticks
   may not be parallel. What may be asynchronous is work whose result does not
   feed a tick, or which lands through the mailbox at a defined boundary.

## Where this applies in v0.2

| Place | What |
|---|---|
| `Column` | geometric growth, never shrink; **swap-and-pop** removal so deleting a row is O(1) and touches two rows, not the tail |
| Archetype graph | add-one/remove-one **edges cached**, so adding a component is a hash lookup rather than a set search |
| `ComponentSet` | **interned**, so archetype identity is an id compare and archetype lookup is O(1) |
| `Query` | matching archetype list held and invalidated only on archetype creation — bounded and rare after warmup. This is what closes `D00003` |
| Entity ids | **free list of recycled indices** plus generations. No allocation per create or destroy |
| `SparseSet` | fixed-size pages allocated on demand and never freed; dense array for iteration |
| Deferred structural changes | one reused command buffer per store, not a fresh vector per `Each` |
| Component registry | sized once at startup. Runtime component creation is refused anyway (§2.4), so the table never grows |
| Mailboxes | ring buffers with retained capacity; payloads from a **per-world arena reset each tick** |
| Inbox ordering | each sender's queue is *already* ordered by `Sequence`, so delivery is a **k-way merge, not a sort** |
| World scheduling | active list reused and sorted **longest-first by last tick cost**, so the parallel batch tail is short |
| Snapshots | double-buffered serialisation buffer per world, reused |
| `ViewChannel` | three slots sized once at the declared maximum payload. No per-frame allocation anywhere in the path |

The arena is worth calling out because it is not a trick, it is the design
already implying an allocator: **§2.7 gives every message a lifetime of exactly
one tick.** A bump allocator reset at the barrier is the exact fit for that
lifetime, and it makes message construction free rather than merely cheap. When
a rule about lifetime already exists, the allocator follows from it instead of
being a separate decision.

## Where this applies in v0.3

| Place | What |
|---|---|
| Broadphase grid | **count-then-fill**: one pass to count per cell, a prefix sum, one pass to place into a single flat array. No per-cell vector, no per-tick allocation |
| Broadphase updates | only re-insert what moved, using `ChangeChannel` stamps. Static geometry is inserted once |
| Sleeping bodies | a `Sleeping` tag **moves the row to another archetype**, so the query never visits it. Better than a per-row branch, and it is the ECS-native form of the optimisation |
| `Anchored` parts | already a separate archetype, so static geometry never enters a dynamic query |
| Pair, contact and manifold lists | cleared, not freed; capacity retained across ticks |
| Solver | **warm-start from a persistent contact cache** keyed by `(entityA, entityB, feature)`. Fewer iterations for the same stability, and the cache is a reuse structure rather than an optimisation bolted on |
| Queries | raycast and overlap write into a caller-provided span, so a system that queries every tick allocates nothing |

## What may be asynchronous

| Allowed | Why it is safe |
|---|---|
| Snapshot writing | serialise into the double buffer at the barrier — a deterministic point — then hand the bytes to a writer thread. The tick never waits on the disk |
| IPC channel drain | pumped at step 2, so arrival timing cannot reach a system |
| Log and telemetry flush | never read by simulation |
| Shader compilation | already off the tick; unchanged |
| Asset loading (v0.7) | lands through a `Ticket`, which is why the ticket exists now |

| Not allowed | Why |
|---|---|
| A system awaiting anything | it occupies a pool worker and stalls the whole world batch |
| A result landing "when ready" | a result that arrives a tick later on a slower machine is a desync |
| Parallel contact solving | nondeterministic visit order, different answer every run (§3.5) |

The distinction is a single question: *can the tick observe when it finished?*
If yes, it is not async, it is a race.

## The caveat

**Preallocation multiplies by world count.** A megabyte reserved per world is a
gigabyte at a thousand worlds, and a universe of small subareas is the case this
whole design is built for. So per-world reservations start small and grow, or
are sized from a declared budget on the world — not chosen once from what a
single big world wanted. A `Suspended` world should release its transient
buffers and keep only its store; that is most of the value of suspending it.

# Open questions

Not blocking, but worth settling before the step that needs them:

1. **Step 6 / 12** — snapshot cadence and retention. Every N ticks is the obvious
   answer; N is a measurement, and both the restart window and the recording size
   follow from it. Same number serves both, which is a reason to pick it once and
   carefully.
2. **Step 8** — does `DataStore` ship v0.2 with an in-memory backing and gain
   durability in v0.7, or wait? The plan assumes the former, with the split
   documented so nobody ships a save on top of a hash map.
3. **Step 11** — how does a `Faulted` world recover: automatic restore from
   snapshot, or does it stay down until something asks? Automatic is friendlier
   and hides a crash loop; manual is honest and needs an operator.
4. **Step 15** — is `PreviousTransform` a component or a double-buffered column?
   The rewrite makes the second option cheap for the first time.
