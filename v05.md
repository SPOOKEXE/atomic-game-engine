# v0.5 — plan

Script bindings, planned before there is a script VM to bind to.

Written the way `docs/retired/v02v03v04.md` was written — before the code, and
against the tree rather than against the roadmap — because v0.5's two roadmap
lines both name inputs that do not exist yet, and finding that out during the
work would turn a describing version into a designing one halfway through.

## The decision this version is built on

**The engine is full ECS. The Roblox surface is a shim, and the shim's whole job
is conversion.**

A component is never reshaped to look like a Roblox property. `Bounds` keeps a
half-extent because that is the form every containment and overlap test wants;
`Transform` keeps one `CFrame` because position and orientation must not be
updatable half-way. **A property is a projection of one or more components**, and
several properties projecting the same component is the ordinary case rather
than a conflict — `.CFrame`, `.Position` and `.Orientation` are three views of
one `Transform`, exactly as `.Size` is a view of `Bounds::HalfExtent` doubled.

Everything below follows from that sentence, and one thing it kills outright is
the model the descriptor table currently implies: a property is **not** a field
at an offset. The field case is the degenerate one, and designing for it first
is what would have forced Roblox's vocabulary back down into the components.

## The two roadmap lines, checked

**Item 1 — "bindings manifest, generated from v0.2's `TypeDescriptor` property
lists and class table, so there is no second source of truth."** The
single-source-of-truth reasoning is right and is why this is worth doing. But
the property lists it generates from **are empty**, so a generator run today
emits four class names, an ancestry chain and no properties. **The generator is
the easy half of this item and the roadmap line describes only that half.**

This is the pattern v0.4 wrote down twice and it is worth naming a third time
rather than rediscovering: *an item written from a plausible mechanism, sitting
unmeasured for a version, is an item whose premise nobody has checked.* Here the
premise is not a measurement but an inventory, and the inventory is zero.

**Item 2 — "plans for luau and typescript multi-threading and multi-processing
systems."** Honest about being a planning item, and it should stay one. Two
corrections to what it plans *over*: it cites `parallel/ipc` and
`parallel/process` as though they were directories, and they are rows in a table
in `parallel/AGENTS.md` marked "arrives with L13" and "arrives with
world-per-process". A plan that cites a path nobody can open is the `CDN.md`
problem this repository already has at the top of `ROADMAP.md`.

## §5.1 What v0.5 actually is

**The version that makes the ECS projectable — describable and writable through
Roblox's vocabulary — so that v0.6 can bind a VM without also designing the
translation.**

v0.6's line is *"`Instance.new`, properties, `.Changed`, the hierarchy and
`:IsA` bind to v0.2's class table — a calling convention, not a second
mechanism."* That is only true if, by the time a VM arrives, the table can
answer three questions it cannot answer today:

1. **What properties does `Part` have?** — nothing has declared any.
2. **What is `Part.Size`, given that no component holds a size?** — the
   descriptor model has no way to say "twice this field".
3. **How do I write `Part.Position` without destroying the rotation stored
   beside it?** — there is no path, and the offset model would let a binding
   write 12 bytes over the front of a `CFrame` and call it done.

Five things, in this order, and the manifest is **last** rather than first:

| # | Thing | Why it is here |
|---|---|---|
| 1 | Make a property a **conversion**, not an offset | The shim's primitive. Nothing below is expressible without it |
| 2 | Widen `PropertyType` to `Vector3`, `CFrame`, `Color3` | The vocabulary the conversions produce and consume |
| 3 | Declare `scene`'s **complete** Roblox surface | The input the roadmap item assumes exists |
| 4 | Get/set by name, through the conversions | The operation, and the manifest's only honest in-repo consumer |
| 5 | Emit and check the manifest | The roadmap item, now with something to describe |

## §5.2 The descriptor becomes a conversion pair

`PropertyDescriptor` today is `{Name, Component, Offset, Type, Size}` and
`Classes::Property` resolves the offset from a member pointer — *"measured rather
than declared, so a field reordered in the struct does not silently point a
binding at the wrong bytes."* That instinct is right and survives; what does not
survive is the assumption that every property **has** an offset.

**The shape: a read and a write, plus the set of components each touches.**

```cpp
struct PropertyDescriptor {
    core::Name Name;
    PropertyType Type;
    uint32_t Size;              // of the userland value, not of a field
    bool Writable;
    bool Structural;            // the write changes the archetype
    ComponentSet Reads;         // what the getter needs
    ComponentSet Writes;        // what the setter touches
    void (*Get)(const void *const *components, void *out);
    void (*Set)(void *const *components, const void *value);
};
```

**One mechanism, not two.** The temptation is to keep the offset form for the
properties that are plain fields and add conversions for the rest — a fast path
and a slow path. Refuse it, for the reason v0.6's own roadmap line gives: *a
calling convention, not a second mechanism*. A plain field's conversion is a
two-line copy, the compiler inlines it into the thunk, and the call is crossing
into a script VM regardless. Two mechanisms is two places for the dirty bit to
be forgotten in.

**What this does not touch, and it is the point of the whole design.** Systems
still iterate typed columns — `Each<Transform, const Motion>` is unchanged, no
conversion runs, and the physics and render paths never learn that a Roblox
vocabulary exists. **The conversion cost is paid only by callers who arrived
through a name**, which is scripts and, later, an editor. Full ECS underneath,
shim on top, and the seam is exactly one indirect call wide.

**`Reads` and `Writes` are not decoration.** They are what lets the manifest say
which components a property depends on, what lets `.Changed` fan a component
write out to the property names that observe it (§5.8), and what a future editor
would use to know that touching `Size` dirties `Bounds` and nothing else.

## §5.3 `PropertyType` and the value types

`Classes.hpp` says adding a case here is *"a decision about what userland can
hold, not an implementation detail — so adding one is a visible change rather
than a template specialisation somebody slips in."* Taking the header at its
word, this is that decision, made in a plan rather than in a commit.

**Add three: `Vector3`, `CFrame`, `Color3`.** These are what the conversions
produce. Without them the manifest is typed for the properties nobody touches
and opaque for the ones every script touches first.

**Do not add `AABB`, `Ray` or `RayHit`.** v0.4 added those for `spatial` and
`physics` to pass around; no property projects to one, and a `PropertyType` case
with no property to describe is the dead vocabulary this enum's comment guards
against. Same reasoning `core/types` used at v0.4 to refuse `Vector2`.

**Note what the conversion model removes from this decision.** Under the offset
model, `PropertyType` had to describe *storage*, so every stored type needed a
case. Under conversions it describes only the **userland value**, so the enum
stays small no matter what the components hold. `LayerMask` never needs a case,
because no property is a `LayerMask` — `CollisionGroup` is a `Name`.

`Classes::TypeOf<T>()` stays as the deduction helper for plain fields, and gains
the three cases. A conversion property states its type outright.

## §5.4 Declaring the complete surface

Where: beside the class registration in `scene/src/Part.cpp`, inside
`RegisterTree()`. Not a new file — the class tree and its projections are one
fact, and splitting them is the second-source-of-truth this item exists to
prevent.

**The names are Roblox's**, which `Part.cpp` already argues for the class tree —
*"v0.6 binds `Instance.new` to this same table and a tree that differs from the
one scripts expect is a migration nobody asked for"* — and the argument is
identical one level down.

Counted against `scene/Components.hpp` rather than guessed:

| Property | Projects | Conversion |
|---|---|---|
| `CFrame` | `Transform::Frame` | identity |
| `Position` | `Transform::Frame` | read/write the translation, **rotation preserved** |
| `Orientation` | `Transform::Frame` | quaternion ↔ Euler degrees — **the getter does not exist yet** |
| `Size` | `Bounds::HalfExtent` | ×2 out, ÷2 in |
| `Color` | `Visual::Tint` | identity, renamed |
| `Transparency` | `Visual` | **no field exists** — open question 4 |
| `Visible` | `Visual::Visible` | identity |
| `Mesh` | `Visual::Mesh` | identity |
| `Material` | `Visual::Material` **and** `Surface::Material` | one name, two components — open question 5 |
| `CanCollide` | `Collider::Mask` | empty mask ↔ `false` |
| `CollisionGroup` | `Collider::Layer` | `Name` ↔ `LayerMask` bit |
| `Anchored` | presence of `RigidBody`/`Motion` | **structural** — an archetype move |

**Every one of these is expressible under §5.2, and that is the finding of this
section.** Four are plain copies. Six are arithmetic or a lookup. One writes two
components. One is structural.

### The module invariant is satisfied, not amended

`scene/AGENTS.md` currently forbids property declarations:

> **No property declarations.** [...] the useful properties do not map to a
> field: Roblox's `Size` is a full extent and `Bounds::HalfExtent` is half of
> one, which a member pointer cannot express. **Declaring the ones that *do* map
> and leaving the rest is worse than declaring none — it reads as a complete
> list.**

Under the offset model that objection is unanswerable and the honest response
would have been a partial list with an "incomplete" flag bolted on. **Under the
conversion model the objection dissolves: a member pointer cannot express a
doubled half-extent, and a conversion can, so the complete list is declarable
and the invariant is met as written.** The bullet is replaced by a statement of
how — not by an exception to it. That is worth recording, because it is a case
where the right move was to fix the primitive rather than to weaken the rule.

### Two things that are genuinely missing

- **`CFrame` → Euler.** `CFrame::Angles(pitch, yaw, roll)` builds a frame from
  intrinsic Y-then-X-then-Z turns. There is no inverse, so `.Orientation`'s
  getter has to be written — and it has to round-trip that exact order, or
  `part.Orientation = part.Orientation` drifts a little every assignment. A
  script that does that in a loop is not hypothetical. **Test: round-trip
  through all three axes at a spread of angles, including gimbal-adjacent
  ones**, before anything else in this section is trusted.
- **`Anchored`'s setter is a structural change**, so it cannot run inline during
  iteration; it goes through the deferral queue the store already has. That is
  the whole reason `Structural` is a field on the descriptor rather than a
  comment: a caller has to be able to know, and the setter has to be refused or
  deferred rather than corrupting an archetype mid-walk.

## §5.5 Get and set by name

The operation the descriptor table exists for, and the piece `ecs/docs/TODO.md`
lists first.

**On `Store`, not on `Classes`.** `Classes` is process-wide description; the
value lives in a world, and a getter that took no store would have nowhere to
read from. This also keeps rule 2 intact — the store owns the storage and this
is a second way in, not a second copy.

```cpp
bool GetProperty(Entity instance, core::Name property, void *out, size_t bytes) const;
bool SetProperty(Entity instance, core::Name property, const void *value, size_t bytes);
```

Bytes and a size rather than a template, because the caller is a marshalling
layer holding a value whose type it learned at runtime. The size is checked
against the descriptor and a mismatch fails rather than truncates — a binding
passing a `Vector3` where a `CFrame` is expected must not write 12 bytes into a
28-byte value and leave the rest.

**Five things this must get right, each of which is a test:**

1. **Composition.** Setting `.Position` preserves the rotation; setting
   `.Orientation` preserves the translation; setting `.CFrame` sets both. This
   is the read-modify-write the projection model demands, and it is the first
   thing an offset-shaped implementation would get wrong.
2. **The dirty bit.** A write must mark every column in `Writes` changed.
   `replication` builds deltas from `ChangeChannel`; a setter that bypasses the
   version stamp is a script write the server never sends, surfacing as a client
   that quietly disagrees. Same class as v0.4's unclipped `EachChangedRuns` run —
   **a corruption with nothing failing** — and the most likely defect in this
   version.
3. **Structural writes.** `Anchored` defers; a structural set during iteration
   must not apply inline. Covered both inside and outside a tick.
4. **`Reference` properties.** An `Entity` is *"a handle within this world, and
   meaningless outside it"*. A setter handed one from another world writes a
   handle resolving to an unrelated or dead entity. Validate, refuse, count.
5. **The adopt-only replica.** A replica store refuses to mint. It must also
   refuse — or at minimum not silently accept — an authoritative property write,
   or v0.6's first client-side script writes a value the server overwrites next
   tick and the symptom is "my script doesn't work sometimes".

## §5.6 The manifest

Now that there is something to describe.

**Format: JSON, generated, checked in, and diffed by the build.** Not a new
pattern — `mono.tools/architecture/expected_graph.json` is exactly it, down to
the comment that says *"a change here is a change to the architecture, and
reviewing the diff to this file is reviewing that change. If a build fails
against it, the question is which of the two is wrong — not which is easier to
edit."* Reuse the pattern and the wording rather than inventing a second
convention for the same job.

**Rule 4 governs the contents.** No `ClassId`, no `ComponentId`, no property
index — those are declaration-order counters and a reordered `add_subdirectory`
would silently repoint every binding. Every identity is a **string**.

**The conversion model makes this easy in a way the offset model did not.** An
offset-based manifest would have had to carry byte offsets — build artefacts
masquerading as identities, needing a caveat in the format about which fields
survive a recompile. A conversion-based manifest carries **no offsets at all**:
the conversion is compiled into the binary and the manifest describes only the
userland surface. Rule 4 is satisfied by construction rather than by disclaimer.

Contents, per class: name, parent, ancestry, component set, whether it is
constructible (§5.8), and per property — name, type, size, writable, structural,
the components it reads and writes **by name**, and the default read off the
prototype row. Those defaults are why prototype rows exist: *"it is the only
form a default can take that a snapshot can carry and the v0.5 bindings manifest
can describe — a constructor function is neither."* That sentence in
`Classes.hpp` was written for this document.

**A version field from the first commit.** v0.4 bumped a snapshot format and
argued one bump beats two; a manifest that ships unversioned makes the first
change to it a format archaeology problem.

**Where the tool lives:** `mono.tools/bindings`. It links `core`, `ecs` and
`scene` — the **first tool to link past `core`**, which every existing row in
`expected_graph.json` shows is a new shape. That row is part of the change, and
reviewing it is reviewing the architecture, per the file's own rule.

### The consumer problem, which is the real risk in this item

**A generated artefact with nothing consuming it rots, and this repository has
watched it happen twice** — `just docs-check` at v0.2, and `just preset=ci
check` at v0.4, where the `docs/DEFERRED.md` entry claiming the checks "are
written and pass" had been half false for as long as it was written down. The
lesson is recorded there in as many words: *if a recipe is named as the
standard, something has to run it.*

At v0.5 the manifest's natural consumer — a VM — does not exist. So name three
that do, and wire them:

1. **A round-trip test.** For every property the manifest lists, drive
   `SetProperty`/`GetProperty` by name and compare against the typed C++ path.
   This catches a wrong conversion, which is the failure that would otherwise
   reach v0.6 as a part that jumps when a script writes its `Position`.
2. **`just bindings-check`, inside `just check`.** Regenerate, diff against the
   checked-in file, fail on drift. Same shape as `test-architecture`, and rule 6
   is what makes it mandatory rather than nice: *a rule the build does not check
   is documentation.*
3. **A docgen page.** The class and property reference, generated from the same
   file, so the documentation site and the bindings cannot disagree.

**Do not add `--script` handling, a stub VM, or an example binding in another
language.** All three are consumers that would have to be maintained without
being run, which is the disease rather than the cure.

## §5.7 Typed declaration files, and how TypeScript happens

Generated from the manifest, checked in, no runtime: a `.d.ts` and a Luau type
file describing the class tree and its properties.

Cheap — the manifest already holds everything — and it is what makes §5.3's
typing decisions *visible* rather than buried in an enum. It is also what v0.6's
example scripts get type-checked against, which is the difference between
`Mirrors-1-world.ts` being a port and being a guess.

The four files in `mono.engine/examples/` are one byte each today, reserving
their names. They stay that way through v0.5.

### TypeScript is a transpile, not a second VM

The roadmap asks for "luau and typescript" in the same breath, and the obvious
reading — embed two runtimes — is the expensive one. **Take the other route:
TypeScript compiles *to* Luau at authoring time, through `roblox-ts`, and the
engine only ever loads Luau.**

What that buys, and each is a cost avoided rather than a feature gained:

- **One runtime, so one determinism story.** A second VM is a second execution
  path through the same tick, and this repository diffs two runs byte for byte.
- **One value model, so one codec.** §5.8's script-value ↔ bytes codec is the
  piece with no prior art in the tree; two VMs means writing it twice and
  keeping the two byte-identical, which is a determinism bug waiting for a
  quiet afternoon.
- **One binding layer.** §5.5's `GetProperty`/`SetProperty` gets marshalled from
  exactly one place.
- **The `.d.ts` this section already generates is precisely what the toolchain
  consumes.** `roblox-ts` takes its Roblox API surface from `@rbxts/types`
  supplied through `typeRoots` in `tsconfig.json` — a *replaceable* type root.
  An engine that is Roblox-shaped but not Roblox substitutes its own generated
  declarations there. `@rbxts/compiler-types` stays, because that one types
  Luau's semantics rather than Roblox's API.

**The objection, and why it does not land.** A Node/npm toolchain at build time
would be a real departure: this repository refused `FetchContent` for Crypto++
specifically so a configure needs no network, and `just setup` is the first
thing a contributor runs. But **the C++ build never sees the TypeScript
toolchain at all** — the compiler emits Luau, and Luau is what ships and what
the engine loads. TypeScript is an authoring choice made outside CMake, exactly
as a text editor is. Nothing in `just check` grows a Node dependency.

**The fallback, recorded so it is not rediscovered.** If a genuine JavaScript
runtime is ever required — a reason that does not exist today — the candidate is
**QuickJS-ng**: MIT, a few C files with no external dependency, an interpreter
rather than a JIT, and reference-counting GC chosen for deterministic behaviour.
It is the maintained continuation of Bellard's QuickJS after the two projects
merged efforts. It is a good engine and it is still a second VM, so the bar for
reaching for it is a requirement TypeScript-to-Luau cannot meet, not a
preference.

## §5.8 The concurrency plan — roadmap item 2

A document, not code.

**"Integration with the hytale setup for worlds" means the Universe/worlds
arrangement: many worlds, processed in parallel, with libraries to cross-message
between them. All of it was built at v0.2 and none of it is reachable from a
script.** So this item is not new machinery — it is the userland surface over
machinery that exists, and the plan's job is to say what that surface is without
inventing a second one underneath it.

What exists, by name:

| Piece | Where |
|---|---|
| Many worlds under one universe | `world::Universe`, `world::World`, `WorldId` |
| Parallel processing of them | `ExecutionMode::WorldParallel` / `WorldSerial`, chosen per host |
| The cross-message library | `world::Postbox` — `Publish`/`Subscribe`, `Get`/`Set`/`Update`/`Remove`, `Push`/`Pop`, `Teleport`, `Deliveries` |
| Four buses behind it | `BusKind::Messaging`, `MemoryStore`, `DataStore`, `Teleport` |
| Correlation | `world::Ticket`, per world and monotonic |
| Process isolation | `world::Supervisor`, `world::HostLink`, `parallel::Process` |

### The decision this item turns on, and v0.2 already took half of it

`docs/retired/v02v03v04.md` §2.7 is titled *"Everything is asynchronous, which
Roblox already taught everyone"*, and argues it exactly this way: every bus call
returns a `Ticket`, the reply lands in the inbox at a later tick, and *"that is
not an engine limitation dressed up — it is the same contract as `:GetAsync()`,
so the semantics a Luau author already expects in v0.6 are the semantics the
engine wants anyway."*

**That settles the shape of the userland API and forces the yield question at
the same time.** A script calling the shim's `GetAsync` cannot get an answer in
the tick it asked, because the reply is applied at a later barrier by
construction. So either the call yields the coroutine — the Roblox answer, and
the one an author expects — or it returns a handle the script polls, which is
not a Roblox shim at all.

**Take the yielding answer, and then owe determinism for it.** Rule 5 says a
result landing a tick later on a slower machine is a desync, and a resumed
coroutine is precisely a result landing later. What makes it legal is that the
*reply* already arrives deterministically — sorted apply at the barrier, which
v0.2 built and `just replay-check` covers. So the rule the plan must write down
is narrower than "scripts may yield": **a script may only resume from something
the barrier delivers in a deterministic order, and resume order within a tick is
part of the recorded run.** A yield on a wall clock, a real timer or an OS event
is the thing that must not exist.

This is also why the item cannot be split from the property work and shipped
later: it is the same `Ticket` a script holds, and the same barrier the property
write lands against.

### What the plan must still settle

Six questions, each with the place its answer already half-exists:

**1. The `thread` contract, stated once.** `parallel/AGENTS.md` already says
`Jobs` is fork-join with no handles and the userland thread *"has to survive a
script yielding"*, and that the two must not merge. The plan cites that; it does
not restate it. What it adds is what a yield *means* against a tick.

**2. What a script may yield *on*.** Settled above in principle: a resume must
come from something the barrier delivers in a deterministic order. What the plan
owes is the list — a `Ticket` reply, a `Deliveries()` entry, a tick boundary —
and the explicit refusal of the others. **`wait(n)` in seconds is the one to
decide first**, because it is the first thing any Luau author writes and a
wall-clock wait is exactly the desync rule 5 names. Ticks, not seconds, is the
answer that survives `just replay-check`; whether it is spelled `wait` or
something that cannot be mistaken for Roblox's is a naming decision with real
consequences for how surprised an author is.

**2b. What a script sends.** Payloads across a bus are bytes — rule 3, and v0.2's
*"trivially copyable structs written through `core::ByteWriter`, or nothing at
all for a bare signal"*. Roblox's `MessagingService` takes a table. **So the shim
needs a script-value ↔ bytes codec, and it must be deterministic**, because the
bytes it produces go into a recorded run that has to replay identically. Table
iteration order is the trap: a codec that walks a hash map in memory order
serialises differently on two runs and breaks `just determinism` far from where
the bug is. This is a v0.5 planning item and a v0.6 build item, and it is the
piece of the cross-messaging surface with no prior art anywhere in the tree.

**3. What a lock can mean — and the roadmap line asks for locks by name.** Rule
3: nothing crossing a world boundary is a pointer. Worlds are the unit of
parallelism and nothing crosses one except a bus message carrying a copy. **So a
userland mutex between worlds is a bus operation, not a mutex** — and the bus
that already implements it is `MemoryStore` with `Update`, which takes a version
and fails `Conflict` when the version has moved on, so the caller re-reads and
retries. **That is a compare-and-swap, which is what a cross-world lock would
have been built out of anyway.** A mutex *within* a world protects nothing,
because a world's scripts are already serialised by its own tick.

Say both plainly, or somebody builds a cross-world lock and ends the
process-per-world option permanently — which rule 3 warns is the failure that is
invisible afterwards.

**3b. Budgets are part of the userland contract, not an implementation detail.**
`BusOperation` already has `OverBudget` and v0.2's reasoning is on the record:
*"Roblox has these because they turned out to be necessary; there is no reason
to rediscover that."* A script that exceeds its per-tick allowance must get a
named, catchable failure — not a silent drop and not a stall. The plan says
which of the shim's calls can fail this way, and what an author is expected to
do about it.

**3c. A replica refuses.** `Postbox::IsReplica()` exists and a replica's bus
handles refuse writes — v0.2 reserved that seam and v0.3 spent it. A client-side
script calling `Set` or `Teleport` must fail visibly rather than appear to work
until the next authoritative tick. Same failure shape as §5.5's rule 5 for
property writes, and the plan should give them one story rather than two.

**4. `synchronise` is the barrier that already exists.** `world::Driver` runs
it. Userland does not get a second one.

**5. Name the paths it will create.** `parallel/threads/`, `process/` and `ipc/`
do not exist; `Process.hpp` and `ProcessChannel.hpp` are what is there. State
the paths the plan intends to add and the moves that implies, rather than citing
a layout as though it were current.

**6. `Ticket`/`Await`.** `world/Bus.hpp` has `Ticket` — per world, monotonic,
zero meaning fire-and-forget. There is **no `Await` anywhere in the tree**. The
plan either defines one over `Ticket` or stops citing it.

## §5.9 Thinking ahead

What v0.5 must leave possible. Each is a constraint on the decisions above, not
future work.

**v0.6 — the VM, and the scene becoming a script.** Needs the surface
describable *and* writable by name, which is why §5.5 sits in v0.5 rather than
travelling with the VM. Because §5.2 makes every property expressible, v0.6
inherits **no property-shaped design debt** — which was not true of the
offset-model plan this document originally carried.

**v0.6 — `.Changed`, and the fan-out the projection model creates.**
`ecs/docs/TODO.md` has the engine half: `OnChanged<T>` is per *type*, Roblox's
`.Changed` is per instance, and filtering a whole-world signal per script would
walk every change for every connection. The projection model adds a second half
nothing has written down yet: **a component write maps to *N* property names.**
Writing `Transform` must fire `.Changed` for `CFrame`, `Position` *and*
`Orientation`, because all three observe it. So the subscription index is not
just entity → connections; it needs component → property names, which is exactly
what §5.2's `Reads` set is. **v0.5 does not build the signal — it builds the
table the signal will need**, and that is the strongest argument for `Reads`
being a declared set rather than something a conversion knows privately.

**v0.7 — worlds rendering in parallel.** §5.8's yield rule is what keeps that
honest; scripts yielding in four parallel worlds is where a non-deterministic
resume order stops being theoretical and becomes a split-screen desync.

**v0.9 — `UserInputService`, `ContextActionService`.** These are **services**:
one instance, reachable by name, not a class you construct. **Nothing in the
class table expresses that** — `Classes` describes classes whose instances you
mint. Either the manifest has room for a service from the start, or v0.9 reopens
the format. Reserve it: a per-class constructibility flag, one field now against
a format bump later. Cheapest item in the document and the easiest to forget.

**Unversioned — attributes.** `ecs/docs/TODO.md` wants a per-entity dynamic
key/value map. **The manifest must not try to describe it** — it is dynamic, so
there is nothing static to describe — and the plan says so, so nobody later
reads the absence as an oversight.

## Decisions taken

1. **A property is a conversion, not an offset.** One mechanism for plain fields
   and computed ones alike, because two is two places to forget the dirty bit.
2. **Components are never reshaped to match a property.** `Bounds` keeps its
   half-extent, `Transform` keeps one `CFrame`. The shim converts; the ECS does
   not accommodate.
3. **The conversion cost is paid only by name-based callers.** Typed iteration
   is untouched, so physics and render never learn a Roblox vocabulary exists.
4. **The complete `Part` surface ships at v0.5**, including `Anchored`. The
   conversion primitive makes it expressible, so `scene/AGENTS.md`'s "declare
   none rather than half" invariant is satisfied as written rather than amended.
5. **`PropertyType` gains `Vector3`, `CFrame` and `Color3`, and nothing else.**
   It describes userland values, not storage, so it stays small.
6. **A descriptor carries the component sets it reads and writes**, because the
   manifest, `.Changed`'s fan-out and any future editor all need them.
7. **`Structural` is a declared field**, so a caller can know that `Anchored`
   defers instead of discovering it by corrupting an archetype.
8. **Get/set by name lives on `Store`**, takes bytes and a size, checks the
   size, and marks every written column changed.
9. **The manifest carries strings only** — rule 4 — and, under this model,
   carries no offsets at all.
10. **The manifest is checked in and diffed by `just bindings-check` inside
    `just check`** — rule 6. Its v0.5 consumers are a round-trip test, that
    check and a docgen page; no stub VM.
11. **A class-constructibility flag ships now**, so v0.9's services do not force
    a format bump.
12. **Roadmap item 2 stays a document**, and builds no new concurrency
    machinery: Universe, parallel worlds and `Postbox` all exist, and the item
    is the userland surface over them.
13. **Scripts yield, and may only resume from what the barrier delivers in a
    deterministic order.** v0.2 made every bus call asynchronous on the
    `:GetAsync()` model precisely so this would be the natural shape; a
    wall-clock or OS-event resume is the thing that must not exist.
14. **A cross-world lock is `MemoryStore::Update`** — a versioned
    compare-and-swap that fails `Conflict` — not a mutex. An in-world lock
    protects nothing.
15. **Luau is the only runtime. TypeScript transpiles to it** via `roblox-ts`,
    so there is one VM, one value model and one codec — and the C++ build gains
    no Node dependency, because the engine loads the emitted Luau.
16. **`Orientation` is degrees**, matching Roblox; `CFrame::Angles` keeps
    radians, and the conversion owns the factor in one place and both
    directions.

## Sequencing

Each step lands building and passing, per the "finish the thing" rule.

| # | Step | Done when | State |
|---|---|---|---|
| 1 | `PropertyDescriptor` becomes a conversion pair with `Reads`/`Writes`/`Structural`; `Classes::Property` keeps the member-pointer form as a generated trivial conversion | `ecs`'s existing instance suite passes unchanged | not started |
| 2 | `PropertyType` gains `Vector3`, `CFrame`, `Color3` | `just determinism` and `just replay-check` byte-identical — the description vocabulary must not move a serialised byte | not started |
| 3 | `CFrame` → Euler, inverse of `CFrame::Angles` | round-trip across three axes and gimbal-adjacent angles | not started |
| 4 | `scene` declares the complete surface in `RegisterTree()`; `scene/AGENTS.md`'s bullet replaced | every property in §5.4's table declared; a suite asserts each against the typed path | not started |
| 5 | `Store::GetProperty` / `SetProperty` | §5.5's five tests, including composition and the dirty bit through `ChangeChannel` | not started |
| 6 | `mono.tools/bindings` emits the manifest; `expected_graph.json` gains its row | manifest regenerates byte-identically twice | not started |
| 7 | `just bindings-check`, wired into `just check` | drift fails the build | not started |
| 8 | `.d.ts` and Luau declarations generated from the manifest | both check in; docgen page renders | not started |
| 9 | The concurrency plan document — the userland surface over `Universe` and `Postbox` | every question in §5.8 has a stated answer, and the document builds no machinery `world` already has | not started |

Step 5 is the risky one. It is the first write path into the storage that does
not go through a typed `Set<T>`, and every safety property the typed path gets
from the compiler — right component, right size, right world, dirty bit — it has
to get from a runtime check instead. Its acceptance criterion is the whole
existing replication suite passing with a script-shaped write in the middle of
it, not just its own tests.

Step 1 is the reversible-by-design one, in the same spirit as v0.2's step 3: the
existing `Classes::Property` member-pointer call site keeps compiling and keeps
meaning what it meant, because a plain field is a conversion the template
writes. If that does not hold, the primitive is wrong and it is cheap to find
out first.

## Open questions

1. **How is `wait` spelled, and does it take ticks?** §5.8 settles that a script
   may only resume from something the barrier delivers deterministically, which
   rules out a wall-clock wait. What is open is the ergonomics: a `wait(n)` in
   ticks under Roblox's name is familiar and quietly different, and a differently
   named call is honest and unfamiliar. The first author to hit it decides
   whether this was a good choice, so it is worth choosing deliberately.
2. **Is the script-value ↔ bytes codec a v0.5 design or a v0.6 one?** §5.8's
   2b. It has no prior art in the tree, it must be deterministic, and it is the
   one part of the cross-messaging surface that cannot be sketched from what
   `Postbox` already does. Recommend designing it in v0.5 with the VM choice
   (question 3), since a codec is written against a value model.
3. **~~Which VM?~~ Settled: Luau, and it is vendored.**
   `mono.vendor/luau`, MIT, added `EXCLUDE_FROM_ALL` so it costs a clone and no
   build time until v0.6 links it. `Vendor::luau_vm` and `Vendor::luau_compiler`
   are the two aliases; `Luau.CodeGen` is deliberately **not** aliased, because
   a native backend is a second execution path for the same script and this
   repository diffs two runs byte for byte — that wants `just determinism` and
   `just replay-check` stated as a test *before* it is enabled, exactly as v0.4
   did before `-O3`. **TypeScript is settled too, and it is not a second VM**:
   `roblox-ts` transpiles it to Luau at authoring time, so the engine loads only
   Luau and the C++ build never sees a Node toolchain — §5.7.
4. **~~`Transparency` has no field.~~ Settled: it becomes a renderer feature at
   v0.6.** `ROADMAP.md` now carries it — a `Transparency` float on
   `scene::Visual`, the same field on `scene::DrawInstance`, and the back-to-front
   sorted pass that makes it mean anything. The component moves for rendering's
   sake rather than the binding's, which is the order this document argued for;
   the property joins the surface when there is something to project onto.
   **v0.5's §5.4 table ships without it.**
5. **~~Which `Material`?~~ Settled by the tree, not by a decision.**
   `Visual::Material`'s own comment already draws the line: *"Distinct from
   `Surface::Material`, which is what it feels like: a mirror-finish floor and a
   rubber floor may share a surface and never a material."* They are two facts
   sharing a name, so `Part.Material` binds to `Visual::Material` alone and the
   physical one needs its own userland name if it ever gets one. Worth recording
   as a small lesson: the ambiguity was in this document and never in the code.
6. **~~Does `Orientation` use degrees?~~ Settled: degrees.** Roblox's
   `.Orientation` is degrees and this surface is Roblox's, so a script that
   works there reads the same number here. `CFrame::Angles` takes radians and
   stays that way — it is the engine's API and the engine's unit — so **the
   conversion is where the factor lives, in exactly one place, and it converts
   in both directions.** The §5.4 round-trip test is what pins it: a getter in
   degrees against a setter in radians is a 57× error that looks like a wildly
   spinning part the first time a script touches it, and looks like nothing at
   all until then.
