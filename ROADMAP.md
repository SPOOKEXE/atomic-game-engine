
# ROADMAP

## Editing

Do NOT add new deferred work as a roadmap item. Place it in
`docs/DEFERRED.md`. If a TODO item is not FULLY completed, split the
TODO item, keeping the concise short dash point list with block infront and
split it as another item under the same version.

For example, if we complete A and B but not C and D:
```
### v0.5
- [x] do: A1, A3, A5
- [_] do: A, B, C, D
- [x] do: G, H, I
- [x] do: K, K2, K3
```

becomes:
```
### v0.5
- [x] do: A1, A3, A5
- [x] do: A, B
- [x] do: G, H, I
- [x] do: K, K2, K3
- [_] do: C, D
- [_] deferred `D0001` for later.
```

or defer to another version.

The gap was in `world` and not in the bindings: `Publish` is a topic fan-out with no destination and `Teleport` names a world but carries a **person**, so a game saying one thing to one world had to broadcast it to everybody or send a player carrying it. `BusKind::Channel` is **appended** beside `Teleport` — these are wire ordinals — and is deliberately not a flag on it: the two look identical on the wire and mean entirely different things to a receiver, and `script::AdmitTeleports` runs on every world whether or not it has scripts, so a channel message arriving as a teleport would have it building a `Player` out of a chat line. A test sends both to one world in one tick and the receiver tells them apart
  - **No `GetWorlds`, stated rather than faked.** A world's storage cannot see its siblings — the directory belongs to the barrier's router — so answering it would mean stamping a world list into every store every tick. `Send` answering false for a world that is not running is the honest half of the same question, and it is the half `Publish` cannot answer at all: a publish with no subscribers is a quiet afternoon and indistinguishable from one nobody wanted
- [x] client-only and server-only, which `ServiceComponent::Scope` had described since v0.7 with **nothing reading it** — it round-tripped through save files and showed in the properties panel while `ServerScriptService` and `ServerStorage` went down the wire to every client that joined. `scene::VisibleToClients` and `scene::PlayerOwning` are the rules, hung on `replication::Authority::SetInterest` by the server, because the wire moves components and has no business knowing what a service is. `SetInterest` did not hand its predicate the world where `SetOwnership` does — a predicate looking up its own world from inside a walk of that world — so the signature widened
  - A test caught the first version being too broad: it hid every player's row from every other client, which reads as a lobby that never fills. The `Player` row is public and what is *under* it is private, which is where Roblox draws it and why
  - **`StarterGui` was not a template at all.** `Layout` drew a `ScreenGui` from `StarterGui` *or* from a `PlayerGui`, so every client drew the same instances — a script hiding one player's health bar hid everybody's. `gui::ResetPlayerGui` does Roblox's rule: collectors with `ResetOnSpawn` true are destroyed and re-cloned, ones set false survive with their state, and a survivor of a name is not cloned beside it. That field had been on `gui::Layer` since v0.8 with nothing reading it. `mono.server` links `Engine::gui` for it — that module depends on `core` and `ecs` and nothing else, and `just check-server-is-headless` still reports no graphics stack
