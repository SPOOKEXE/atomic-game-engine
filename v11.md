# v0.11 — plan

Three roadmap lines, and they are not three independent pieces of work: two of
them are the same change seen from different ends, and one of the two is
half-built already. What follows is the order that falls out of that, and the
evidence for it.

## 1. The document this plan cannot follow

The roadmap line says *"`RENDER_PIPELINE.md` stages 8 to 12, including the HDR
and G-buffer prerequisite its §17 opens with"*.

**That document is not in this repository and never has been.**
`git rev-list --all --objects` finds no such path, which `ROADMAP.md` already
says at the top for five design notes at once. So stages 8 to 12 cannot be
followed by number, and this plan does not pretend to.

This has happened once before and the precedent is the right one: v0.6's graph
entry records that *"`RENDER_PIPELINE.md` is not in this repository — so 'stages
1 to 7' could not be followed by number and the line's own text was built to
instead"*. The same is done here. Every stage named below is derived from what
`render` and `graph` actually contain, and where a name is borrowed from the
missing document it is marked as a guess.

**If that document can be produced, this section is the first thing to revisit** —
not because the plan would change shape, but because a stage list somebody else
already reasoned about is worth more than one reconstructed from the consumer.

## 2. What is actually there, checked rather than remembered

- **`graph` is a description with no executor.** Four headers, 431 lines of
  source: `Frustum`, `Cull`, `Shadow`, `Pipeline`. `Pipeline` holds `Stage`
  records with `Reads`, `Writes`, `PerView` and `Optional`, and `Validate`
  checks one property — a stage reading what nothing earlier wrote. Nothing
  runs it. `Renderer` calls `graph::Cull` and `graph::FitDirectionalLight` as
  **functions**.
- **`Stage::PerView` exists and nothing reads it.** Its own comment says it is
  *"the distinction that decides how many worlds cost"* — a shadow map is per
  light and shareable, a colour pass is per view and is not. It was written for
  exactly the work this version is about.
- **`Renderer::Render` takes one view.** One camera, one draw list, one overlay,
  one target slot — and **twelve parameters**, four of them added since v0.9.
  `Renderer.cpp` is 4,462 lines.
- **The frame is described twice**, which is `D00016`: `render::PassOrder` names
  six passes and `graph::StandardPipeline` is the same six as data, kept in step
  by a test that compares them and by a sentence in an `AGENTS.md`.
- **`bake::Graph` is already a working node runtime.** Input, processing and
  export nodes; topological order; cycles refused at the wire; at most one input
  per node so provenance is a walk; `MAXIMUM_NODES` 4096; **and it touches no
  filesystem**, so all of it is exercised headlessly.
- **Physics and spatial are instrumented.** `Broadphase`, `Integrate`,
  `NarrowPhase`, `Solver` and `HashGrid` all have benchmarks. The broadphase
  already splits dynamic from static and rebuilds the static index only when the
  static set changes.
- **`render` has one benchmark and it is `Overlay.cpp`.** There is no
  measurement of a frame at all.
- **No node-editor library is vendored.**

## 3. The constraint that decides the order

**Item 1 changes what the stages *are*; item 2 changes what *runs* them.** Doing
the executor first means writing it against a stage list that is about to gain
HDR and a G-buffer — and `graph/Pipeline.hpp` says in as many words why that list
was left short: *"both change what every later stage reads — adding them now
would be writing a pipeline for a renderer that does not exist."* Doing HDR first
means editing the hand-rolled function again, which is what `D00002` is a
standing complaint about.

The way out is that item 1 has two halves that separate cleanly:

- **The multi-view seam** — `Render` taking a *list* of views instead of one.
  This is the half `D00002`'s trigger names: *"handle multiple worlds in parallel
  is the first roadmap line that cannot be met by making the function longer."*
  It changes no stage.
- **HDR and the G-buffer** — new targets and new stages, which changes the list
  but not its shape.

So the seam goes first, the stages second, the executor third — by which point
the list it executes has stopped moving. **`render::Viewport` was tried at v0.7
and deleted inside the same version as the wrong primitive**; that is the warning
this ordering is built around, and §4.1 says what is different this time.

Item 3 is independent of all of it and can land whenever.

## 4. The work

### 4.1 One frame, many views

`Render` becomes `Render(std::span<const View>, FrameSettings)`, where a `View`
carries what today's twelve parameters carry per view — camera, instances,
surfaces, particles, ribbons, lights, target slot — and `FrameSettings` carries
what is per *frame*: the overlay, the interface hook, the present decision.

**Why this is not `render::Viewport` again.** That type was a rectangle — a
projection and a scissor — and it failed because it described where a view lands
rather than what a view *is*. It was replaced by the scene target it should have
been part of. A `View` here is the whole input to one pass sequence, and the test
of whether it is the right primitive is whether `Stage::PerView` can be read
against it. That flag is the thing that has been waiting.

What this buys immediately, and what should be measured before and after:

- The studio draws N panels in N `Render` calls, round-robin, so **each panel
  refreshes at a fraction of the frame rate**. v0.7 decided that deliberately and
  named its revisit condition: *"when a viewport is expensive enough that its
  record is measurable."* Nobody has measured it — which is the first task, not
  the second.
- Shadow maps are recomputed per call today. `PerView = false` says a shadow pass
  is shareable across views of one world; four split-screen views should pay one
  shadow map, and today they pay four.

**A frame benchmark comes first.** `render` has none, and an item about GPU
traffic that starts by changing the frame without one is this repository's own
worst pattern — v0.4 rejected a data-layout change on a measurement and v0.2's
chunked-storage item was *moved* by one.

### 4.2 HDR and the G-buffer

Two new targets and the stages that read them. This is where the missing document
would have earned its keep; absent it, the minimum that has a caller here:

- A floating-point colour target, a tonemap stage before the overlay, and
  `Visual`'s colours reinterpreted as linear rather than as whatever the
  swapchain format meant.
- A G-buffer only if something reads it. **The roadmap's own rule applies to its
  own plan**: v0.8 refused `VideoFrame` and `Path2D` because a registered thing
  nothing draws is worse than its absence. A G-buffer with no deferred lighting
  pass and no post chain is the same shape. So the honest scope is HDR plus
  tonemap, and the G-buffer arrives with its first consumer — which is most
  likely the clustered light pass `opaque.frag` already names as v0.11's
  replacement for its sixteen-light loop.

Each new stage lands in `render::PassOrder` **and** `graph::StandardPipeline` in
the same change, because `tests/Passes.cpp` compares them and fails otherwise.

### 4.3 The executor — `D00002` closed, `D00016` deleted

`graph` grows the runtime half: nodes, resource handles, a compiled order and an
executor that `Renderer::Render` calls instead of submitting six passes by name.

**This is the change that removes the second description rather than checking
it.** `D00016` says so explicitly and says not to action it separately: *"a
runtime deletes the second description rather than checking it, so doing this
entry separately buys a third copy of a mitigation that is already a sentence in
an AGENTS.md and a comparison in a test."*

The shape `bake::Graph` already proves out, and reusing its decisions rather than
re-deriving them is most of the value:

- Cycles refused when the edge is added, not discovered at run time.
- The graph owns no device resource; it decides *what*, and `render` does it.
- Topological order, with the executor holding the only knowledge of a device.

**What must not be copied** is `bake::Graph`'s one-input rule. A render node
reads several attachments; that constraint exists in the baker because a bake
chain is a pipeline and provenance should be a walk, and it is wrong here.

### 4.4 The two node editors

**Assets Pipeline is a view of a runtime that already exists.** `bake::Graph` has
the nodes, the wiring, the validation and the execution, and it is headless by
construction. The widget is a canvas, a node list and a property panel over an
object the engine already builds — plus a serialisation format for a saved graph,
which `bake::Graph` does not have and which is the actual new work.

**Render Pipeline is a view of §4.3 and cannot precede it.** Drawing a node
editor over `graph::Pipeline` as it stands today would be a picture of a flat
list — there are no nodes to draw.

Both need a decision this plan cannot take on its own: **whether the node canvas
is a vendored library or the engine's own `gui` tree.** Nothing is vendored
today. Vendoring `imgui-node-editor` is fast and puts the studio further into
imgui at exactly the moment v0.8 started moving its panels onto the engine's own
tree; building it on `gui` is the direction of travel, has no dependency, and is
considerably more work. See §6.

### 4.5 Physics spatial optimisations

The smallest of the three and the only one with measurements already in place.
The candidates, in the order the existing benchmarks can justify them:

- **The broadphase pair walk**, which v0.4 measured getting *7.8% worse* at `-O3`
  — one of the handful of paths that regressed when everything else halved.
- **The static index rebuild**, already change-gated, and the dynamic one, which
  is rebuilt whole every tick.
- **`spatial::HashGrid` cell sizing**, which is a constant nobody has re-measured
  since it was chosen.

**Nothing here should be touched before a number says so.** This repository has
twice moved a roadmap item on a measurement that contradicted it, and the
physics benchmarks exist precisely so this item is not guesswork.

## 5. What is deliberately not in v0.11

- **A general dependency-resolving frame graph.** `Pipeline.hpp` argues against
  it at this size and the argument still holds at ten stages.
- **Deferred lighting**, unless the clustered pass lands and wants it.
- **Skinning**, which is v0.9's open line and not this one's.
- **Replacing the studio's imgui panels.** v0.8's TypeScript property grid is the
  proof it can be done; doing it is its own version.

## 6. Open questions

1. **`RENDER_PIPELINE.md`** — does it exist outside the repository? If it can be
   produced, §4.2's stage list should come from it rather than from this plan.
2. **The node canvas** — vendored `imgui-node-editor`, or built on the engine's
   own `gui` tree? This decides how much of §4.4 is UI work.
3. **Physics** — is there a scene that is actually slow, or is this item
   pre-emptive? The first changes what gets optimised; the second means the work
   starts with a benchmark that reproduces a complaint nobody has made yet.
