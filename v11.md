# v0.11 — plan

## 1. The roadmap line asks for stages that cannot be done here

The line reads *"`RENDER_PIPELINE.md` stages 8 to 12, including the HDR and
G-buffer prerequisite its §17 opens with"*. The document is at
`../atomic-game-engine-hidden-docs/RENDER_PIPELINE.md`, 2,022 lines, and reading
it changes what this version is.

**Those stages belong to a different codebase.** §16 is a staging plan for a
graph renderer being built *beside an existing one*: stage 8 is "switch the
default, keep `--renderer=v1` as the escape hatch" and stage 8b is "strip v1 and
rename". §18 is titled *Stripping v1 and the rename*. Throughout, the document
describes machinery as already built — `ChainCache` as a stub, `ExecContext`
carrying the camera, `Camera.Shaders` entries becoming chain nodes,
`Camera:Render()` providing a readback, and **box3d** as the physics engine.

None of that is this engine. Checked rather than assumed — of the document's own
named artefacts, the number of files in this repository mentioning each:

| `NodeDesc` | `ExecContext` | `ChainCache` | `SceneParts` | `GeometryNode` | `SwapchainPresent` | `CapabilitiesOf` | `ClearPolicy` | `--renderer=v2` |
|---|---|---|---|---|---|---|---|---|
| 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |

`ShaderScript` matches once, in a comment in `ShaderCompiler.hpp` that refers to
the concept.

**§16 records stages 1, 3 and 5 as done. They are done there.** Here, the whole
of `graph` is four headers and 431 lines: `Frustum`, `Cull`, `Shadow` and a
`Pipeline` that is a flat list of stage records with a read-before-write check.
That is a fragment of stage 1's *validation* and none of its storage, handles,
resource table or interpreted executor. There is one renderer, no `--renderer`
flag, and nothing to switch a default away from.

So **stages 8 to 12 are not the work**. Stage 8 is a one-line default flip
between two renderers this repository does not have. What v0.11 can honestly do
is the document's **stages 1, 3 and 5**, adapted — the skeleton and executor,
capabilities, and porting the passes — followed by **stage 10** (the editor) and
then **11 and 12** (the HDR prerequisite and the frame content) if there is room.

The roadmap line should be corrected rather than quietly reinterpreted. `D00004`
and `D00001` are both in the register because a number inside them drifted; a
roadmap line pointing at stages that cannot be started is the same failure with
more consequence.

## 2. Two of the document's stated blockers are already retired here

Worth stating first, because they are the reason this is tractable at all.

- **§17: "Runtime shader compilation depends on shaderc, which the engine does
  not yet link ... treat any claim about runtime compilation or permutation
  caching as unproven."** This engine links it. v0.1 shipped
  `render::ShaderCompiler` over vendored libshaderc, and `render`'s
  `CMakeLists.txt` carries `VENDOR SDL3::SDL3 shaderc`. The blocker that makes
  their stage 6 and §11.9.1 unverifiable does not exist here.
- **§14 / §16: "Physics-tick separation is independent of all of this and can
  land at any point; it is probably worth doing early, since it changes what
  every frame-time measurement means."** Done at v0.1 — `core::FixedTimestep`,
  `Scheduler::RunPhases`, interpolated rendering, both rates on F3.

A third is half-retired: §17's *"box3d still has no shapes, so nothing
collides"* has no analogue — this engine has its own narrow phase with six
analytic pairs.

## 3. What this repository actually has

- **`graph` describes and does not execute.** `Renderer` calls `graph::Cull` and
  `graph::FitDirectionalLight` as functions.
- **`Stage::PerView` exists and nothing reads it.** Its comment calls it *"the
  distinction that decides how many worlds cost"* — a shadow map is per light
  and shareable, a colour pass is per view and is not. It was written for this
  version.
- **`Renderer::Render` takes one view** — one camera, one draw list, one target
  slot, **twelve parameters**, four added since v0.9. `Renderer.cpp` is 4,462
  lines.
- **The frame is described twice** (`D00016`), kept in step by a test.
- **`bake::Graph` is a working node runtime** — input, processing and export
  nodes, topological order, cycles refused at the wire, no filesystem access, so
  all of it is exercised headlessly.
- **`render` has one benchmark and it is the overlay.** There is no measurement
  of a frame.
- **No node-editor library is vendored**, and per §6 the canvas will be built on
  the engine's own `gui` tree.

## 4. The work

### 4.1 A frame benchmark — first, and not as ceremony — **DONE**

§17: *"A graph can be slower than the code it replaces. Per-node dispatch,
hashing and cache lookups are real overhead, and at the current profile added
CPU work is exactly the wrong direction ... stage 1 will almost certainly be
slower than v1."*

There is no before-number for a frame in this repository. Building one is the
first commit, and it also settles v0.7's open question — the studio draws N
panels in N `Render` calls round-robin, and that was decided deliberately with a
stated revisit condition: *"when a viewport is expensive enough that its record
is measurable."* Nobody has measured it.

**Landed as `render/benchmarks/Frame.cpp`.** It composes the sequence
`Renderer::Render` performs above the first render pass — resolve, extract,
cull, bound, gather, order, partition, group, sign, order the scene range — and
runs it for one, two and four views. Everything it calls is `shared`, so it
needs no GPU.

| Row | Cost | Per view |
|---|---|---|
| Extract a frustum | 42 ns ± 1 | |
| Record one view, 5000 instances | 145 us ± 3 | 145 us |
| Record two views, 5000 instances | 298 us ± 17 | 149 us |
| Record four views, 5000 instances | 617 us ± 54 | 154 us |
| Record four views, bound hoisted | 680 us ± 11 | 170 us |
| Record one view, 20000 instances | 782 us ± 23 | |

Three results, and two of them change what follows.

1. **A viewport costs ~150 us of CPU record, so v0.7's condition is met.** Four
   panels are 617 us — 3.7% of a 60 fps frame but **18% of a 300 fps one**. The
   round-robin decision now stands on a number rather than an assumption.

2. **Hoisting the union bound out of the cull is a *pessimisation*, by 10%.**
   This was the obvious `PerView = false` candidate and the row was added to
   confirm it. It does the opposite. `graph/benchmarks/Cull.cpp` already had the
   reason: nine of a culled instance's seventeen nanoseconds are
   `AABB::FromOrientedBox`, and the cull needs that box regardless — so
   `CullAndBound`'s fusion *is* the optimisation, the union is six comparisons
   on a box that already exists, and a shared node re-derives five thousand
   boxes to save them. **So the thing worth sharing is the shadow *pass*, not
   the shadow *fit*** — which is the line `graph::StandardGraph` already draws.

3. **The `BENCH` harness's iteration count means two different things in two
   files** and nothing in a report says which. Filed as `D00037`; it cost the
   first run of this benchmark, which reported a frame at 739 ns.

### 4.2 One frame, many views — **SEAM DONE, NO MULTI-VIEW CALLER**

`render::View` replaces the twelve parameters, and `Render` takes
`std::span<const View>`, an `OverlayImage &` and a `FrameOverlayHook *`. One
command buffer, one swapchain acquisition, one present, N views.

What moved to frame level, each because a view could not own it:

- **`windowTarget`** starts the frame asking to `CLEAR` and the first view that
  draws onto the window flips it to `LOAD`. Four window views must not each
  erase the last.
- **`PassRecorder`** grew `BeginView`. Its `Ran` mask is the union over the
  frame; its *position* resets per view, because four viewports submit shadow →
  surface → opaque four times and a recorder that kept climbing would report the
  second view's shadow pass as out of order. This is `D00016`'s coupling showing
  up as a concrete defect, and it is why §4.3 follows.
- **The interface upload** happens once, after every view — a copy pass cannot
  open while a render pass is in flight, and the hook has one vertex buffer.
- **The overlay** is ensured and uploaded once, before the loop, in its own copy
  pass. It was per view, and left that way an empty `views` would have drawn no
  panels — which is exactly the frame an editor with every viewport closed
  presents.

**Verified byte-identical.** `just studio-smoke` renders headlessly to a BMP and
that capture is reproducible run to run, so it is a golden: `studio-smoke.bmp`
hashes to `51931c79…` before and after the change, including after the overlay
hoist. (`studio-meshes.bmp` is *not* reproducible — 700 frames of async mesh
streaming — so it is not usable as one.) Ignoring re-indentation the whole
restructure is 222 changed lines in `Renderer.cpp`.

**Nothing passes more than one view yet**, and the studio cannot until the
surface-aiming order is resolved. Filed as `D00038`.

### 4.2 (original plan)

`Render` takes a span of `View` rather than one camera and eleven trailing
parameters. **The document settles the design question this raises**, and it is
the one it calls *"the assumption most likely to be wrong, and cheapest to change
now"*:

> **Settled: whole-frame, with one chain region per distinct chain shape.** …
> Keying regions on a chain signature gives the cross-camera sharing … two
> cameras whose chains resolve alike share one run of nodes.

So: one graph per frame, per-view subgraphs, regions keyed on a signature, and a
node able to say "not this camera" cheaply. `Stage::PerView` is what marks the
difference, and four split-screen views of one world should pay for one shadow
map rather than four.

**Why this is not `render::Viewport` again.** That type was added and deleted
inside v0.7 as the wrong primitive — it was a rectangle, describing where a view
lands rather than what a view *is*. The test of the new one is whether
`Stage::PerView` can be read against it.

This is `D00002`'s stated trigger: *"handle multiple worlds in parallel is the
first roadmap line that cannot be met by making the function longer."*

### 4.3 The skeleton and the executor — **SKELETON DONE, EXECUTOR OPEN**

`graph::RenderGraph` is built and tested: nodes over named resources,
`Validate`, `Compile`, `Execute`, and a `NodeRunner` seam so L9 links no device.
39 headless cases in `test_graph`. The partition is the point — four views run
**one** shadow pass and four opaque passes.

The design had to be corrected mid-build. It began as a producer→consumer
topological sort and the standard frame refused to compile: `opaque` writes
colour, `transparent` draws onto it, `overlay` onto that, `interface` onto that,
so all four read *and* write colour and dependency edges over them form a
four-node cycle. And it is not a tangle to untangle — which of overlay and
interface goes on top is **authored**, and no analysis recovers it. Declaration
order is the execution order; the resources are a *check* on it.
`GraphStatus::Cycle` was deleted as unreachable.

**The second description is deleted, so `D00016` is closed.** This is the part
that had to land with the graph rather than after it — the entry says doing it
separately "buys a third copy of a mitigation", and the graph had briefly made
it exactly three.

- `render::PassOrder()` reads its names out of `graph::StandardGraph()`.
- `graph::Pipeline`, `StandardPipeline` and their tests are **deleted**;
  `RenderGraph` supersedes them entirely.
- `tests/Passes.cpp` is repurposed: it can no longer compare two descriptions,
  so it checks the derivation against the hand-written `Pass` enum.
  Mutation-verified — swapping `overlay` and `interface` in `StandardGraph`
  fails it at both the count and the position.

**Then wiring the renderer to it exposed a modelling error, which is what that
work is for.** `StandardGraph` had `overlay` and `interface` as `PerView = true`,
and they are not — they draw onto the *window*, once, after every view. Two
things had to change and both fell out of the existing principle rather than
needing new machinery:

- **`CompiledGraph` grew a third block.** A real frame has shared work at *both*
  ends: a shadow map before any view samples it, an overlay and an editor's
  chrome after every view has finished. Two lists can only put shared work at
  one end, and putting the overlay first draws it under the world. Which end a
  node lands at is **its declaration position** — before the first per-view node
  or after the last — so there is no third field to keep in step. A shared node
  strictly *between* per-view nodes cannot be expressed by three blocks and is
  refused as `SharedBetweenViews` rather than silently hoisted.
- **`colour` and `window` are separate resources.** They were one, and the
  `SharedWriteConflict` check fired on the standard frame — correctly. A view
  draws into whatever target it was given; the overlay draws onto the swapchain.
  Conflating them said the editor's chrome fought the world for the same memory.

A second check earned its keep on the way: declaring `interface` as *reading*
the window made switching the overlay off a `ReadsBeforeWrite`, i.e. "the chrome
cannot be drawn without the debug panels". Wrong — the renderer clears the
window when no pass touched it, so its initialisation is the frame's job, not a
node's output. What keeps the chrome above the overlay is declaration order.

44 cases, 485 assertions. The end-selection is mutation-verified: forcing every
shared node to the front fails three assertions across two cases.

**What is still open is the executor**, which is `D00002`'s remainder: `Render`
still submits six passes by name rather than running the graph through a
`NodeRunner`. The description is now accurate enough to run — which it was not
before this — but the submission has not been moved onto it. Until it is, a pass
added with an inline `SDL_BeginGPURenderPass` is invisible to all of the above,
the one hole `D00016` always named.

### 4.3 (original plan)

`graph` grows nodes, handles, a resource table and an interpreted executor;
`Renderer::Render` runs the graph instead of submitting six passes by name.

**This deletes the second description rather than checking it**, which is what
`D00016` says to wait for: *"a runtime deletes the second description rather than
checking it, so doing this entry separately buys a third copy of a mitigation."*

`bake::Graph` is the shape to reuse — cycles refused at the wire, no device
resource owned by the graph, topological order. **Its one-input rule must not be
copied**: that exists so a bake chain's provenance is a walk, and a render node
reads several attachments.

### 4.4 The editor — **API DONE FOR ASSETS, UI NOT STARTED**

§13.1 and §6 both settle that the API comes first and the UI consumes it. That
API now exists for the Assets Pipeline half, as `bake::GraphDocument`.

**Editing operations are data.** `bake::Operation` is one record — add a node of
some kind, or wire two — and `bake::Document` is an ordered list of them.
Replaying builds a `Graph`; writing saves it; dropping the last entry is undo.
One representation, four features, no second description to keep in step. A
script can build a pipeline with no UI at all, which is what §13.1 asks for.

Decisions worth recording:

- **A document is a recipe, not a payload.** `Graph::AddSource` takes bytes; the
  document takes a *name* and `Build` asks a `SourceResolver` for the bytes. A
  document that embedded its inputs would be a save file the size of the assets
  and would go stale when the file changed. It also keeps `bake` off the
  filesystem, so all 88 cases run headless.
- **Wires name document positions, not `NodeId`s.** A `NodeId` is whatever the
  runtime issued, so a saved graph carrying one would only reload into a graph
  built in the same order by the same code.
- **The text format is line oriented**, one operation per line, so a saved
  pipeline reviews as a list of what somebody did. `game::Xml` is L10 and `bake`
  is L9, so it could not have been used even if the shape suited.
- **Names are quoted and escaped**, and that is load-bearing rather than tidy: a
  built-in named `cube\nwrite "stolen.amesh"` would otherwise add a node nobody
  asked for. Mutation-verified — deleting the newline escape fails exactly that
  case.
- `Read(Write(d)) == d` is asserted against **every** operation kind, because
  the failure it guards is a field written and not parsed, which is invisible
  until somebody saves the one pipeline that uses it. Floats go through
  `std::to_chars`, so a scale of a third reloads bit-identical.

**The Render Pipeline half now has the same layer**, as
`graph::PipelineDocument`. Deliberately the same shape as `bake`'s — record,
replay, write, truncate-to-undo — because two editors that agreed about nothing
would be two sets of bugs. The escaping rules are held identical for the same
reason.

What differs is the vocabulary, and it had to: `bake::Graph` wires an output
into an input, so its document has `connect`; `RenderGraph` has no wires, so
this one has `resource`, `reads` and `writes` — the same information stated the
way the runtime states it. `enable` is there because `SetEnabled` was written as
an operation rather than a field precisely so a pass somebody switched off
survives a save.

Two decisions worth recording:

- **`Build` compiles the graph before returning `Ok`.** A document that produces
  a graph nothing can run is a broken save file, and saying so at load is the
  difference between a diagnostic naming the node and a frame lit by whatever
  was in that memory. Mutation-verified — removing the compile check fails two
  cases.
- **`StandardDocument()` is the real frame as edits**, and the headline test
  builds it and checks it compiles to the *same three blocks, node for node*, as
  `StandardGraph()`. So the format is checked against the frame the engine draws
  rather than only against fixtures somebody wrote for it.

62 cases and 548 assertions in `test_graph`.

**And `graph::PipelineSet` holds many of them**, which the roadmap line asks for
directly: *"many node trees in one editor"*, and for render *"as different
subpipelines"*. A world does not have *a* pipeline any more than it has *a*
script — a main chain, a cheaper one for a reflection, a debug one somebody
switches to.

- **Names come back sorted**, so a set written twice with the same contents is
  byte-identical whatever order an editor added things in. That is what makes a
  save diffable, and it is mutation-verified: appending instead of inserting in
  order fails four assertions.
- **`Set` replaces rather than refuses**, unlike `RenderGraph::AddResource`. A
  duplicate resource inside one graph is an authoring mistake with no sensible
  reading; saving over a pipeline is what "save" means.
- **A set and a document do not read as each other** — different first words, so
  a reader knows which shape it holds from the first line rather than from
  whether a `pipeline` line ever turns up.
- The set's body is emitted through the document writer with its header
  stripped, so the two formats cannot drift into spelling an edit differently.

**And `graph::PipelineView` is the read-only widget's data**, which §4.4 calls
the stage worth having alone: columns, bands and edges, computed with no UI in
front of them so the thing deciding where a node is drawn can be wrong in a test
rather than on somebody's screen.

**The edges have to be derived, and that is the one real decision in it.**
`bake::Graph` wires an output into an input and its editor draws what it was
given; `RenderGraph` deliberately has no wires — a node names resources and
never names another node. So an edge is **the last writer before a reader**:
when a pass reads colour after both `opaque` and `transparent` wrote it, the
line comes from `transparent`, because that is what it will actually see.
Drawing one from every earlier writer would fill the canvas with lines that are
true about the resource and false about the data. Reads resolve before the
node's own writes are recorded, which is what stops `transparent` — which reads
the colour it also writes — being joined to itself. Mutation-verified: swapping
those two loops fails three cases.

**What the widgets still need decided is where they live.** A panel builds `gui`
instances (L7) from a `graph::PipelineLayout` (L9), so it needs both, and
neither is above the other in a useful way:

- **Not in `graph`.** It is `shared` and links no UI; giving it `gui` to draw a
  canvas would put presentation in the module a headless host uses for culling.
- **Not in `gui`.** It would have to link `graph` and `bake` to know what a
  pipeline is, which is a layout library growing opinions about render passes.
- **`studio` is the natural home** and is where the panels already are — but
  every other piece of this version was built so it could be exercised
  headlessly, and the studio is the one place that is hardest to test. The
  layout being separate is what keeps the untestable part down to instance
  construction and input.

The likely answer is a small module above both — the same argument `render`
makes for keeping `scene::OrderScene` in `shared`: *"a renderer is the one
module a test cannot exercise, so the counts it hands to a draw call are the
last place they should be computed."*

**Still to do**: both widgets, on the `gui` tree, and the two roadmap lines
added at the user's request — the pipeline becoming a property of a *world*
rather than the process (`D00040`), and worlds persisting their pipelines in
export data. Everything those need to call now exists and is tested headlessly;
what is missing for persistence is a dependency edge from `game` to `graph`, a
named resource registration, and the XML wiring.

### 4.4 (original plan)

§13.1 settles this too, and agrees with the choice made in §6:

> **Settled: in-engine, driven by Luau.** … the API comes first and the UI is a
> consumer of it, which also means a graph can be edited from a script with no
> UI at all.

And the rule that makes it worth building in that order: **editing operations are
data.** `AddNode`, `Connect`, `SetParam`, `Group` as records rather than methods
on a panel — which is what gives serialisation, save/load, undo and scripted
construction for free, and is why the panel is a consumer rather than an owner.

Their three UI stages are the right order and the first is worth having alone:
read-only view (topological columns, edges, per-node milliseconds, cache hit or
miss, dead-with-reason), then inspection, then editing.

**Assets Pipeline is a view of a runtime that already exists.** `bake::Graph` has
the nodes, the wiring, the validation and the execution. What it does not have is
a serialisation format for a saved graph — that is the actual new work, and it is
the same operations-as-data decision one module over.

**Render Pipeline cannot precede §4.3.** Drawn today it would be a picture of a
flat list.

Two things from §13.0 to carry over rather than rediscover: three node flavours
that fail differently — `Cpp` trusted and declared, `Shader` safe by construction
because SPIR-V reflection means *a user cannot mis-declare what it reads*, `Luau`
untrusted and CPU-only — and the load-bearing restriction that a Luau node is
called **once per stage, never once per part**: *"a Luau call per part at skygrid
scale is 131072 crossings of the C++/Luau boundary per frame. That is not a slow
node, it is a hang."*

### 4.5 HDR and the G-buffer — their stage 11, if there is room

§17 is unambiguous that this lands as a unit: *"a G-buffer without HDR targets,
or MSAA without the stencil work, is a half-converted frame that is worse than
either end state."* And that nothing in §11 is reachable before it.

The same argument this repository already makes for itself: `graph/Pipeline.hpp`
left HDR and the G-buffer out because *"both change what every later stage reads
— adding them now would be writing a pipeline for a renderer that does not
exist."*

So it is scoped as one landing or none, and it is the last thing in the version
rather than the first.

### 4.6 Physics spatial optimisations — **MEASURED; DO NOT OPTIMISE**

The section was scoped benchmark-first precisely so it could not turn into
tuning by vibe. The benchmarks answered the question that was asked and then
answered a better one.

**The cell-size question is settled.** `spatial::HashGrid::DEFAULT_CELL_SIZE` is
4 m and the broadphase suite had noted that its scene would prefer 8 m, without
the evidence to move a default another module owns. That evidence now exists —
the ladder runs at 1000, 4000 and 16000 colliders, and 8 m wins at all three
with the minimum bracketed by a 16 m row.

**The default still should not change**, because `spatial` measured a different
workload: `OverlapBox` is fastest at 4 m and costs 42% more at 8 m, and short
raycasts prefer 4 m too. Only rebuilds and long raycasts want bigger cells. Two
workloads, two optima, which is exactly why `PreparePhysicsWorld` takes a cell
size instead of assuming one.

**And then the finding that ends the section: nothing calls
`PreparePhysicsWorld`.** `RegisterPhysicsSystems` is called only from physics'
own tests. No shipped world runs a broad phase, a narrow phase or the solver at
any cell size. The four production `physics::Raycast` sites are not reached in
the default scenes — a headless `studio --run play` and a 60-tick server run log
zero of the every-call error an unprepared world produces.

So the solver's 13.7 ms at 800 stacks, and the broadphase's 2.6 ms at sixteen
thousand colliders, are honest measurements of code no frame executes. **Taking
a percentage off either buys nothing.** Filed as `D00039`; the order is wiring
first, then measuring against a real world's density rather than a synthetic
slab.

### 4.6 (original plan)

Pre-emptive — nothing has been reported slow. So this starts with benchmarks at
realistic counts to find where the cliff is, and touches nothing a number has not
pointed at. Candidates the existing suites can already speak to: the broadphase
pair walk, which v0.4 measured getting **7.8% worse** at `-O3`; the dynamic index
rebuilt whole every tick where the static one is change-gated; and
`spatial::HashGrid`'s cell size, a constant nobody has re-measured since it was
chosen.

## 5. What is deliberately not in v0.11

- **Fusion.** §17: *"Fusion is the dangerous pass … gated on the
  interpreted-mode oracle. If that oracle is not built, fusion should not be
  built either."* The oracle is the interpreted executor in §4.3 and it will be
  new.
- **Their stages 2, 4 and 6** — caching, growth catches, the compiler. §16
  records them as not started there either, and §4.1's measurement is what would
  justify any of them.
- **Deferred lighting and the AA stack**, which are §11 and downstream of §4.5.
- **Replacing the studio's imgui panels.**

## 6. Decisions taken

1. **`RENDER_PIPELINE.md` is available** and §1 above is written against it.
2. **The node canvas is built on the engine's own `gui` tree**, not a vendored
   library — which agrees with §13.1's "in-engine" and makes the node editor the
   second real consumer of `gui` after v0.8's TypeScript property grid.
3. **Physics is pre-emptive**, so it begins with a benchmark rather than a fix.
4. **The frame benchmark comes first**, then the multi-view seam.
