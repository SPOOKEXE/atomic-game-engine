# v0.10 — plan, and the record against it

What `ROADMAP.md` v0.10 asked for, the order the dependencies actually ran in,
and — from §5 on — what happened when it was run. The shape is `docs/retired/v07v08.md`'s:
reasoning first, file list second, because the file list is the obvious part once
the reasoning is settled.

The version has two halves and they were not planned together. The first is the
one this document was written for: particles, attachments, sequences, the camera
and the character. The second is the one the first half's own success created —
a content store with two thousand assets in it, and an editor that could not use
them. §6 is that half, and it is written after the fact because none of it was
foreseen.

The roadmap listed eighteen bullets and they were not eighteen independent pieces
of work. Three things gated most of the rest:

- **`Attachment` is the fence post.** Beams, trails and particle emitters are all
  parented to one in the vocabulary this engine is copying, so a version of any
  of them built before it exists is a version that gets rebuilt.
- **The sequences are already here.** `core::NumberSequence` and
  `core::ColorSequence` have existed since v0.6 with a fixed twenty-keypoint
  capacity, an `Envelope` field nothing reads, and Luau bindings. What v0.10 adds
  is the *keypoint* constructors, the `ecs::PropertyType` cases that let one be a
  property, and the first consumer — which is the particle emitter.
- **The particle system decides the render architecture, not the other way
  round.** 100,000 emitters at five particles each is half a million particles a
  frame. That number rules out every arrangement where a particle is an entity, a
  `DrawInstance`, or anything with a `core::Name` in it.

---

## 1. The scale constraint, settled first

**A particle is not an entity and must never become one.** At half a million
particles an `ecs` row per particle is half a million archetype rows churning
every frame — create and destroy are the two operations an archetype store is
worst at, and a particle's whole life is one of each. `physics/AGENTS.md` already
makes the neighbouring argument for why a sleeping body moves archetype rather
than carrying a flag; this is the same reasoning pointed the other way. Particles
are pooled in a resource and the *emitter* is the entity.

**A particle is not a `scene::DrawInstance`.** That type is 80 bytes and carries
two `core::Name`s, a full `CFrame` and an `AlphaMode`. Half a million of them is
40 MB written per frame, and none of the fields is one a particle varies: every
particle from one emitter shares a texture, a blend mode and an orientation rule.
So the emitter carries what is shared and the particle carries what is not.

`ParticleInstance` is **28 bytes** (the plan said 32 — see §5), and each field is
there because it varies per particle within one emitter:

| field | bytes | why per-particle |
|---|---|---|
| `Position` | 12 | it moved |
| `Size` | 4 | `Size` sequence over its own age |
| `Rotation` | 4 | `RotSpeed` integrated over its own age |
| `Colour` | 4 (RGBA8) | `Color` and `Transparency` over its own age |
| `Frame` | 2 | flipbook cell, from its own age |
| `EmitterSlot` | 2 | which emitter's texture and blend state to draw with |

**Storage is a slab of pooled arrays, not a `std::vector` per emitter.** 100,000
vectors is 100,000 allocations and 100,000 pointer chases to reach one particle.
The pool is one array of `ParticleState` (velocity, age, lifetime, seed) and one
of `ParticleInstance` (the presentation half), indexed the same way, with each
emitter owning a contiguous **capacity block** assigned when it starts emitting.

**Dead particles are swapped to the end of their own block, not compacted
globally.** A global compaction is a data dependency across every worker; a swap
inside a block touches only that block's memory and keeps the live prefix
contiguous for the upload.

**The emitter's own randomness is per-emitter, never global**, so two runs of one
scene emit the same particles — the determinism rule applied to the one system
whose whole job is to look random.

## 2. The order of work

### Group A — the vocabulary the rest needs

1. **`core::Vector3::One`**, and `zero`/`one` on the Luau and TypeScript
   `Vector3`.
2. **`NumberSequenceKeypoint` and `ColorSequenceKeypoint` constructors** in both
   bindings. The types existed and the keypoints were unreachable from a script,
   which made a twenty-stop gradient unauthorable.
3. **`ecs::PropertyType::NumberSequence` / `ColorSequence` / `NumberRange`.**
   `PropertyType` is a closed list on purpose and growing it is a visible change:
   three cases in `game::Values`, three widgets in the properties panel, three in
   each binding. A particle emitter has eight sequence properties and none of
   them can be a property until this lands.
4. **`Enum.Material`**, replacing `Enum_Material` in the generated bindings — a
   change to `mono.tools/bindings` and to nothing else.

### Group B — `Attachment` and `Attributes`

5. **`scene::Attachment`** — a `CFrame` relative to a parent `BasePart`, plus the
   resolved world frame, **derived once a frame by a system rather than per
   read**, because a beam reads both of its attachments' world frames every frame
   and a getter that walked to the parent would be two tree walks per beam.

   This is the one place the "every transform is world space and nothing
   propagates it" rule gets an exception, and it is worth stating why it is not
   one: an `Attachment` is not a `PVInstance` and carries no `Transform`. There
   is still no transform hierarchy and no dirty cascade — one flat pass over one
   component type.

6. **`ecs::Attributes`** — an arbitrary name to an arbitrary value, which is
   exactly the shape a component column cannot hold, so it is a **resource** keyed
   by `(Entity, Name)` rather than a component. That keeps `Instance`'s component
   set the size it is and the value union out of the archetype.

### Group C — lights, beams, trails

7. **`scene::Light`** — one component with a `LightKind`, because three
   components would be three columns, three queries and three upload paths for
   what the renderer packs into one array either way.
8. **`effects::Beam` and `effects::Trail`** — both are ribbons between two
   points. A beam is a ribbon between two attachments with a Bezier through it; a
   trail is one *sampled over time*. One ribbon builder, two sources of points.

### Group D — the particle system (the bulk)

9. **`mono.engine/effects`**, a new module at **L8 · shared**, beside `physics`.
   Shared rather than client because a server simulates particles for anything
   gameplay reads off them, and because a headless test is the only way this gets
   checked at all.
10. **The renderer's particle pass.** A billboard quad expanded in the vertex
    shader from `gl_VertexIndex` — no vertex buffer for the quad at all. One
    instance buffer, sorted back to front when the emitter blends and unsorted
    when it adds.
11. **The stress scene**, `Particles.luau`. The roadmap's number is the
    acceptance test.

### Group E — camera, character, input

12. **`CurrentCamera`** on `Workspace`, a `Reference` property over the
    `ActiveCamera` resource.
13. **`scene::CameraController`** — the resource holding camera mode, zoom and
    clamps. The *arithmetic* is in `scene` (shared, testable); the *events* come
    from `input` (client).
14. **`scene::InputState`** — a shared resource written by the client from SDL,
    read by scripts. This is the seam `UserInputService` needs: `input` is L12
    client and `script` is L9 shared.
15. **`UserInputService` and `ContextActionService`** over that resource.
16. **`scene::Humanoid`** and a character controller, kept deliberately small.

### Group F — the CDN folder and the assets manager

17. **`~/Documents/atomic-game-engine/cdn/{raw,baked,processed}`**, hash-named,
    with a log file. `cdn::LocalStore` becomes the default source for the cdn
    service, the client and the studio.
18. **The upload button and the uploaded-asset browser**, in `mono.studio`.
19. **Seed the folder**, and **GIF support** — a decoder in `bake` producing a
    flipbook texture, which is the same shape the particle flipbook needs and is
    why the two are in one version.

## 4. What is deliberately not in v0.10

- **A GPU particle simulation.** The step is a CPU parallel loop and the upload
  is per frame. A compute-shader step is the right answer at ten million and the
  wrong answer at half a million, because at this size the upload dominates.
- **Particle collision.** It needs a broad-phase query per particle. The property
  is not declared, rather than declared and ignored.
- **The node editors** in the v0.11 bullet.
- **Inline rendered thumbnails for meshes.** See §6.

## 5. What actually landed, against this plan

**Done and verified** — every one of v0.10's items. 208 test suites pass, both
languages typecheck, the architecture graph and the bindings drift check agree,
`just format-check` is clean, and `just determinism` and `just replay-check` are
byte-identical.

**`Enum.Material` was `[~]` and is not.** The first pass concluded Luau could not
express a dotted type, probed a definitions file, got "Unknown type", and filed
it as impossible. The probe was right and the conclusion did not follow: a
definitions *file* cannot declare one, and the **host** can register one — which
is what Roblox does. `DEFERRED.md` D00028 carries the correction rather than
being deleted.

### What the plan got wrong

- **`ParticleInstance` is 28 bytes, not 32.** The table in §1 was arithmetic done
  by hand and the compiler disagreed. A `static_assert` now pins it.
- **The plan said the sequences' `Envelope` field was "what it was put there
  for".** It is sampled at spawn for `Lifetime`, `Speed`, `Rotation` and
  `RotSpeed` — but those are `NumberRange`s, not sequences, so `Envelope` still
  has no consumer. The field remains unread.
- **§1 said the emitter's randomness would be `core::Random`.** It is not:
  `core::Random::Float` is a SHA-256 per number, and a scene emitting twenty
  thousand particles a second would run two hundred thousand SHA-256 blocks a
  second to decide where smoke goes. What was kept is the property that mattered.

### What only running it found

The plan reasoned carefully about the simulation and said nothing about the draw,
and every one of the four real bugs was on the other side of that line:

1. The render pass issued **one draw call per emitter** — 1,608 on a
   1,600-emitter scene, and would have been 100,000 at the target.
2. The upload memcpy'd into the transfer buffer and **never issued the copy**. It
   drew the previous frame's contents, so it took a screenshot rather than a
   crash.
3. The refresh pass re-sampled four curves per emitter per frame and was **70 per
   cent of the frame** — 6.4 million `Evaluate` calls for tables that do not
   change.
4. The stress scene's own host parts were `Transparency = 1`, which *submits*
   them into the sorted blended pass: a hundred thousand invisible cubes sorted
   back-to-front every frame, at 4 FPS.

## 6. The content half, which the plan did not contain

Group F was two bullets and a seeding step. What it produced was a store of 1,973
assets, and everything downstream of that number broke in a way no test covered,
because every test used a store with four things in it. This section is the
record of that, written afterwards.

### 6.1 The store's own shape is the thing to understand first

**A store is flat and hash-named, in both halves.** `raw/` holds
`<64 hex><extension>` because `ImportFile` renames on the way in; `baked/` holds
the same because `assetc` writes a content hash. The published manifest carries
those exact strings. So **the id is the hash**, and
`MeshPart.MeshId = "7d64f772….amesh"` is not a workaround for a missing id system — it *is* the id
system, and it was there all along.

That has consequences the plan never stated:

- **A list of names is a list of identifiers nobody can read.** This is why the
  picker needs thumbnails at all, and why "just show the name" was never an
  option.
- **A name is the only thing that crosses** — rule 4 — so an id copy-pastes
  between two parts, into a script, or out of a note, and nothing has to resolve
  it first. Two parts naming one id are two `DrawInstance`s carrying one interned
  `core::Name`, which `MeshTable::Resolve` answers from one entry and one upload.
  Counting how many name an id is counting instances; there is no per-part copy
  of geometry to find.

### 6.2 Nothing is fetched by kind

Requesting by kind stopped working the moment the store got large, and it failed
twice in two different ways.

**Textures hit a ceiling.** `render::TextureTable::MAXIMUM_BYTES` is 512 MB and
an uncompressed 1K sheet is four megabytes, so 1,637 of them spend it after about
a hundred and forty. The rest were refused in *manifest* order, which has nothing
to do with what a scene names — so the texture somebody asked for was usually
among the refused, and the only trace was 1,463 identical warnings.

**Everything else hit a stall, which is worse.** The unit that travels is a
**bundle**, and that is the right design — per-asset requests would be thousands
of round trips. It means asking for every mesh and material by kind asks for
essentially every bundle in the store, and `AssetClient::Pump` resolves, fetches,
verifies and decompresses all of it **synchronously**, because
`delivery/Client.hpp` forbids a background thread: a completion arriving at a moment
scheduling chose would be a desync. On this repository's store that is 6.9 GB
through one function on the frame the editor opens — a 29-second start-up.

So: **a world names it or it is not fetched.** Start-up went 29 s → 1.44 s, and a
scene naming one mesh fetches one mesh in 26 ms.

**"Asynchronously" cannot mean a thread here.** What it means is that the
*asking* is spread: a bounded number of new requests per pump, over an idempotent
collection, so what is not issued this pump is issued on the next and there is no
queue to keep in step.

### 6.3 The picker wrote nothing, for a whole version

The editor's asset picker — the panel this version added so that a hash-named
store could be browsed at all — **discarded every choice made in it**.

`game::WriteProperty` refuses a value whose `Type` does not match the
descriptor's, on its first line, before it looks at the store. The panel built a
`game::PropertyValue` from nothing, set `Name` on it, and left `Type` at its
default of `Opaque`. So a confirmed pick was dropped one call short of the world,
for `MeshId`, `TextureID`, `MaterialId`, `SoundId` and `Image` alike.

**Nothing reported it.** `WriteProperty`'s `false` is used only to decide whether
an undo entry is worth recording, so a refused write and a write that changed
nothing are the same non-event. What a person saw was: `MeshId` stays blank, the
`MeshPart` keeps drawing `MeshTable`'s fallback cube, and a texture never appears
on it — three separate-looking bugs, one cause. And every one of the three is
*also* what unfetched content looks like, which is why it read as a broken
pipeline rather than as a broken panel.

Three things came out of the fix, and the second is the one worth keeping:

1. The type is carried across the frames the modal is open (`Editor::PickerType`).
2. **`studio::ChosenContentValue(type, chosen)` exists**, and the panel and the
   tests both call it. Taking the type as a parameter is the fix — a caller can
   no longer forget it, because there is nowhere to put a name without also
   saying what kind of property receives it. Assuming `PropertyType::Name` inside
   would work today and would be the same coincidence that broke it.
3. The editor's content summary is logged **whenever the totals change**, not
   once. An editor is not a client: a client names its content at load and stops,
   so one line described the whole session. An editor's whole job is to name
   content later, and the once-only version reported `0 mesh(es)` on the frame the
   catalogue opened and then never spoke again.

### 6.4 One id space, and the engine's own end of it

`MeshTable::Initialise` registers six generated meshes — `engine.Cube` through
`engine.Cylinder` — before any delivery client exists. They are the geometry an
editor can *always* resolve, and until now nothing in the editor could reach
them: the mesh picker listed the published manifest and nothing else, so on a
machine with no store it was empty. A picker that appears not to work, rather
than a store that is not there.

Four pieces of code read a `MeshId` and they now agree by asking
`assets::BuiltinFromName` the same question:

| reader | decision |
|---|---|
| `AssetPicker` | whether to *offer* it |
| `Editor::RequestContentAsset` | whether to *fetch* it |
| `MeshPreview` | how to *load* it for a picture |
| `render::MeshTable::Resolve` | what to *draw* |

The disagreements are silent in both directions: a built-in fetched from a CDN is
a guaranteed miss logged as though content were broken, and a store asset handed
to `MakeBuiltin` is a cube where a dragon should be.
`mono.studio/tests/MeshResolution.cpp` holds all four, with no store and no delivery client.

`MeshGrid.luau` is now the third world of the new-game template, and it seeds
from those six ids. **It costs nothing at start-up, which is the only reason it
can be there**: a built-in is generated in-process and never requested, so the
world names six meshes that are already registered and issues no request at all.
A template that pulled content on open would put back the 29 seconds §6.2 spent a
version removing.

### 6.5 What is left, stated rather than implied

- **A mesh has no inline thumbnail.** Rows show a glyph; the *hovered* row gets a
  real render, and that now covers built-ins as well as store meshes. A cached
  rendered thumbnail per mesh needs the renderer to copy a slot's target into a
  retained texture, which it does not expose — that is a renderer change, not a
  studio one, and it is not in this version.
- **A scene cannot ask what a store published**, only what its world already
  loaded. Since §6.2, the catalogue holds what something asked for — so a scene
  that only reads the catalogue can never be the thing that asks.
  `MeshGrid.luau`'s content half therefore only fills for a place that already
  names imports. Listing the manifest to a script is the content-browser work in
  `ROADMAP.md`.
- **The assets manager's upload is a typed path rather than a file dialog**,
  because there is no portable picker in this stack.
- **Five Poly Haven materials were skipped** at import for having no diffuse map,
  and one asset failed to bake. The failure was not identified.
