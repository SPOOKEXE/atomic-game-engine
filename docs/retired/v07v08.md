# v0.7 / v0.8 — plan

The editor. What `mono.studio` gets now, what it gets at v0.8, and what is
deferred with the version it is deferred to.

Written **after** the code rather than before it, which inverts
[`docs/retired/v02v03v04.md`](v02v03v04.md) and
[`docs/retired/v05.md`](v05.md) and is the point: v0.7's editor exists,
runs, and was read against a live build before any of this was written. Every
defect named in §2 was reproduced in a running studio, not inferred from a source
file. That is the only reason the order in §5 is worth anything — a plan that
guesses which half is broken sequences the wrong half first.

## Documents referenced from here that are not in this repository

`MCP.md` and `RBLX_STUDIO.md` are cited by section number below and are design
notes held outside the tree, same as the five `ROADMAP.md` names at its top. A
citation here is a pointer somebody has to be handed rather than one they can
follow. Said once, rather than qualified at every citation.

## 1 · What this is planning against

Every item below is bounded by rules already in force in `mono.studio/AGENTS.md`.
They are restated here as constraints rather than cited, because three of them
change what an item *is* rather than how it is written.

| Rule | What it costs an item below |
|---|---|
| Nothing in this program is world state | Undo's command log, the selection, gizmo mode and snap settings live in `Editor`, never in a store. A command log that entered a snapshot would be restored by Stop and would then describe a universe that no longer exists |
| Every panel draws inside `Universe::Enter` and acts from outside it | A gizmo drag cannot write a `Transform` where it is drawn. It records into a `Pending*` and `ApplyPendingActions` writes it. This is the single most load-bearing constraint on §4.6 |
| The viewport is a texture in a panel, and the image is **last frame's** | An overlay drawn over that texture must be projected with the matrix that produced it, not with the current camera. See §4.2 — this is the item most likely to be got wrong |
| Every panel is closable, and the View menu is the only way back | Every panel added in §4 and §6 goes into `DrawViewMenu` in the same change, not a follow-up |
| Bump the dockspace version when you add a panel, **and not otherwise** | v0.7 adds several panels and rearranges the default layout. That is **one** bump to `StudioDockSpace.v6`, batched, because every bump costs everybody their layout |
| The class picker never hard-codes a class | The command palette in §4.8 walks a registry for the same reason. A palette with a written-out command list is a second place to forget something |
| A widget's id comes from its label | Script tabs, palette rows and inspector rows all pin ids with `###` to the instance, never to the text |

And one from `ROADMAP.md` v0.8, which is a scheduling constraint rather than a
code one: **`mono.studio` keeps Dear ImGui until the engine's own UI can draw a
property grid.** Everything in §4 is therefore imgui, deliberately and not as a
stopgap to apologise for.

## 2 · What the running build actually does

Reproduced against `just mcp` on a 1920×1048 window, empty universe, two worlds.

**What is good and should not be disturbed.** The panel set is right: two
viewports, Explorer, Worlds, Properties, Script Editor, Output, Settings,
Statistics, Frame Graph. Explorer and Properties both carry fuzzy filters.
Explorer has ctrl-multiselect and drag-drop reparent. Properties groups by
declaring class, root first. Keybinds are a real editable table with scopes.
Worlds is a per-scene transport rather than a global one. None of that needs
rework; §4 adds to it.

**What is broken, in the order it was found.**

- **The status bar is submitted every frame and cannot be seen.** `DrawStatusBar`
  runs *after* `DockSpaceOverViewport` and carries `NoBringToFrontOnFocus`, so
  docked panels paint over it. It is computing fps, draw calls, triangles, culled
  count and camera speed for nobody. **This is the same bug the comment at
  `Interface.cpp:137` records having already been fixed for the toolbar** — the
  toolbar was moved *before* the dockspace so that it shrinks the work area, and
  the status bar never got the same treatment.
- **Modals do not re-centre.** Resizing the window left the New World dialog at
  its old absolute position, hanging off the bottom-right corner.
- **There is no grid, no ground plane and no origin axes.** An empty world is a
  black rectangle. No scale, no horizon, no indication of where the origin is or
  which way is up. `grep -i grid` over `mono.studio/src` returns only the
  *SkyGrid* world's name.
- **The default layout is wrong in its proportions.** Viewport at 606×742 beside
  Viewport 2 at 991×358; the Script Editor holding a large empty block; Explorer
  opening *behind* the Worlds tab, which is the wrong one of the two to have in
  front.
- **The toolbar is text.** No icons, no tool modes, no snap, no camera speed —
  and camera speed is in the status bar nobody can see.
- **Every file dialog is a typed path.** Open, Save As, Import World, Import
  Universe, Export World, Export Universe all present one text field and expect a
  full path, with no browsing, no recents and no validation until the button.
- **Output has no filter, no search, no source and no jump.** It is a correct log
  view — monospace, colour by level, pinned-to-bottom only when already there —
  with none of the things that make a log searchable.

## 3 · Three findings that change the order

### 3.1 · The mutating `Editor` methods are the command log's seam

*(Corrected during v0.7's implementation. This section originally claimed the
seam was `ApplyPendingActions` and `ApplyPendingWorldActions` — that every
mutation passes through those two functions. **It does not.** `InsertInstance`,
`DeleteSelection` and `DuplicateSelection` each have three callers spread across
`Explorer.cpp` and `Interface.cpp`: the appliers are one caller among several,
and the menu and the shortcut reach them directly. The check §"What would make
this plan wrong" asked for is what found it.*

*The conclusion survives in a better form. The mutations are concentrated in a
small set of `Editor` methods rather than scattered across call sites, and
recording **inside those methods** catches every caller at once — which is
strictly better than recording at the appliers would have been, because it covers
the paths that never reach them. What follows is the argument as it should have
been written.)*

`Editor` carries roughly fifteen `Pending*` fields and two appliers,
`ApplyPendingActions` and `ApplyPendingWorldActions`. That structure exists for
`Universe::Enter`'s affinity check, not for undo — but it means **every mutation
this editor performs already passes through two functions, from outside the
store, in a known frame phase.**

So the command log is not a fifty-call-site retrofit. It is a record written where
those two appliers already run, and the inverse computed where the forward
operation is already assembled. The rule in `AGENTS.md` — *adding an action means
adding a `Pending*` field* — becomes *adding an action means adding a `Pending*`
field and its inverse*, which is one sentence longer and enforces itself the same
way.

**This is why undo is early in §5 rather than late.** It is cheapest now, before
gizmos, palette operators and multi-instance property edits each add mutations
that would otherwise have to be retrofitted one at a time. The half-undo
`AGENTS.md` warns about — property edits covered, deletions not — is precisely
what building it after those three produces.

### 3.2 · One operator table, three consumers

`Keybinds::Action` is an enum of eleven editor commands, each already carrying a
name, a description and a scope. `MCP.md` §3 argues separately that a studio
operator — name, parameter schema, poll, execute, description — **is an MCP tool
descriptor field for field**, and that the poll function is the valuable part
because it turns availability into something an agent reads before acting rather
than discovers by failing.

The palette wants exactly that record. So `Action` generalises into an operator
table with a poll, and **three consumers read one registry**: keybinds, the
command palette, and the studio's MCP surface. Building the palette against its
own hand-written list would create the second place to forget a command, which is
the mistake the class picker is written to avoid.

The poll function also fixes something visible today: menu items are enabled by
hand-written conditions at each call site — `!Selection.empty()`,
`Universe->Count() > 1`, `Active.IsValid()`. Those are the poll functions, written
inline, once per site, with nothing comparing them.

### 3.3 · Two stated blockers are stale

- **The monospace font exists.** `mono.studio/AGENTS.md` defers syntax
  highlighting and the line gutter partly on "*a monospace font is a file this
  repository does not have and a licence somebody has to choose*". It is
  `mono.vendor/fonts/JetBrainsMono.ttf`, OFL, already deployed to
  `studio/fonts/`, already loaded as `ui::Typeface::Monospace`, and **already
  used by the Output panel**. The licence was chosen. Only the highlighting is
  actually outstanding. *(`AGENTS.md` needs this line corrected under its
  important-changes exception; this document does not edit it.)*
- **Gizmos are not gated on v0.8.** `ROADMAP.md` v0.8 places viewport selection
  and gizmos after `GuiBase3d` adornments, which is right for the *engine's*
  adornment classes — `SelectionBox` and `Handles` are instances a game can
  create, and they belong with the gui tree. But the editor's own gizmo is not
  one of those. Drawing it in imgui now is consistent with "`mono.studio` keeps
  Dear ImGui until the engine's own UI can draw a property grid", because that
  sentence is about the studio's panels, not about whether the editor may draw a
  line. The engine adornments still arrive at v0.8 and are still the right home
  for the *scriptable* versions.

And one finding that is not a blocker but is an absence worth naming: **the
studio's MCP surface cannot see the studio.** Six tools — `engine_info`,
`world_list`, `world_tree`, `instance_get`, `instance_set`, `profile_frame` — all
of which describe the universe and none of which describe the editor. An agent
can read the world and is blind to the interface in front of it. `AGENTS.md`
already says why the obvious fix does not work: `--headless` starts the imgui
context but not its backends, so panel drawing is skipped entirely.

## 4 · v0.7 — what happens now

### 4.1 · The bar that was there all along

`DrawStatusBar` moves **before** `DockSpaceOverViewport` and becomes a
`BeginViewportSideBar(ImGuiDir_Down)`, exactly as `DrawToolbar` already is at the
top. That is the whole fix; the content is already correct.

Modals move to re-centring on the main viewport each time they appear rather than
once. The dialog set is already one shared `PathPrompt` shape for five questions,
so this is one place.

**A status bar that is visible earns more content**, and the two obvious
additions are what the selection is and what the camera is doing — but camera
speed is already there, so the addition is the selection: how many instances, of
what class, in which world. It is the readout the explorer cannot give while you
are looking at the viewport.

### 4.2 · Ground, and knowing where you are

A grid, the three origin axes, and a horizon.

**Drawn into the viewport panel's imgui draw list, not as a render pass.**
`mono.engine/render` has no debug-line facility at all — `DrawLine`, `DebugLine`
and `Wire` return nothing across its headers — so the alternative is a new
primitive path at L12 for an editor-only need, and `render` is not where an
editor's furniture belongs.

**The trap, and this section had it wrong.** The paragraph here used to say that
the panel shows *last frame's* texture — quoting `AGENTS.md` — and concluded that
each `ViewportState` should retain the view-projection that produced it so the
overlay shares the same one-frame lag. Reading the frame actually disproves the
premise, and the correction is worth more than the original:

- `DrawViewport` records the panel's draw list at `Interface.cpp:182`.
- `DriveCamera` updates the camera at `Interface.cpp:214` — **after** it, because
  it needs the hover and active state the viewport's `InvisibleButton` produces.
- `PresentWorld` renders the world *after the whole imgui frame*, with that
  updated camera, into the same command buffer with the world pass first — which
  is what `DrawViewport`'s own comment at `Interface.cpp:594` says: the texture
  sampled is usually **this** frame's picture, not the previous one's.

So the pixels under the overlay come from the camera as of *this* frame's
`DriveCamera`, and an overlay projected during `DrawViewport` is one
`DriveCamera` behind them. Retaining the previous matrix would have locked in the
lag rather than removed it.

**The fix is to defer the overlay, not to retain a matrix.** `DrawViewport`
records the panel's `ImDrawList` and rectangle; the overlay is appended to that
same draw list after `DriveCamera`, still inside the imgui frame, projected with
the camera the renderer is about to use. The lag is zero rather than shared.

That also removes a duplication the retained design needed: the far plane does
not enter the x/y projection at all — for a perspective matrix the divide is by
`w = -z_view`, which depends on neither near nor far — so the overlay does not
have to reproduce `PresentWorld`'s `FarPlane = max(FarPlane, reach * 40)`
adjustment to stay aligned with it. Only field of view, aspect and the camera
frame matter, and the near plane only for clipping.

The second trap survives the correction unchanged, and is in `Renderer.hpp:213`:
the renderer reports how much of a slot's texture the world was drawn into, which
is not necessarily the whole texture. Panel space maps to *that sub-rect*, not to
the panel rect. Everything in §4.6 depends on the same mapping.

Both are now `studio::PanelProjection` in `studio/Projection.hpp`, which is pure
arithmetic — no imgui, no store, no device — and `tests/Projection.cpp` covers
the round trip, the aspect ratio, the sub-rect offset, the behind-camera refusal
and the near-plane clip. A third trap turned up while writing those: clipping a
grid line against a small epsilon `w` rather than against the **near plane** puts
the cut point at the eye, where the perspective divide produces coordinates in
the millions and imgui rasterises them as a stripe across the viewport.

### 4.3 · The layout and the toolbar

`BuildDefaultLayout` is rewritten and `DOCKSPACE` becomes
`StudioDockSpace.v6` — once, covering every panel added anywhere in this plan.

- Viewport is the central node. **Viewport 2 is a tab beside it, not a split.**
  A second viewport is something you switch to far more often than something you
  watch simultaneously, and the current 606×742-against-991×358 split is what
  wanting both at once actually looks like when neither is sized for it.
- Right, top: **Explorer in front of Worlds.** Explorer is the panel you work in;
  Worlds is the one you visit.
- Right, bottom: Properties.
- Bottom: Output, Script Editor, and the v0.8 inspectors as further tabs in the
  same node so that adding them later is a tab rather than a re-split.
- On demand and undocked by default: Settings, Statistics, Frame Graph, palette.

The toolbar gets icons, weighted separators, the tool-mode group from §4.6
(select / move / rotate / scale), snap toggles with their step values, and camera
speed. Camera speed moves here from the status bar because it is a control and
not a readout, and the status bar keeps reporting it.

### 4.4 · Files and the log

**A file browser written in imgui over `std::filesystem`, not a vendored
dialog.** `mono.vendor` holds nothing for this and the candidates each bring a
platform surface — a native dialog is a second event loop on one platform, a
portal round trip on another. The editor is already imgui, the browser is a table
and a path bar, and it works identically on every platform the studio builds for.
The trade being accepted: it will not look like the host's file dialog. Recents,
a default directory per operation, extension filtering and validation before the
button all come with it, and those are the things actually missing today.

Output gets a level filter, a text search over the same `FuzzyMatch` the two
existing filters use, a source column, and click-to-jump for any line carrying a
script and a line number — which is the one that turns the panel from a log into
a debugger's front door.

### 4.5 · Undo, first and not last

A command log in `Editor`, per §3.1.

- One `Command` record: a description for the palette and the Edit menu, a
  forward application and an inverse.
- Written where `ApplyPendingActions` and `ApplyPendingWorldActions` already run,
  which is outside `Universe::Enter` and in a known phase.
- **Bounded, and it holds no `Entity`.** An entity is an index into one store and
  a generation; a command that survives a Stop and then names an entity is naming
  something else. Commands key on `StableId` and resolve at apply time, and a
  command whose target no longer resolves is dropped rather than applied to
  whatever now occupies the row.
- **Play clears it.** Stop restores a snapshot taken before the run; an undo
  stack that spanned that boundary would offer to undo edits that the restore has
  already discarded. The log is per edit session, and the transport says so.
- Cross-world moves — `MoveInstanceToWorld`, which writes a document out and
  rebuilds it on the far side — invert as the same operation in reverse, and the
  handle changes both ways. The selection is repointed and script tabs are closed
  on undo exactly as they are on the forward move, because that code path already
  exists for the forward case and having one is the reason it is not "sometimes".

### 4.6 · Picking, gizmos, camera

**Picking is a ray and one call.**
`spatial::Raycast(grid, ray, maxDistance, mask)` already exists over the proxy-box hash grid, and `core::Ray` and
`core::RayHit` have been in `core/types` since v0.4. So a click builds a ray from
the panel-space position through the retained view-projection of §4.2 and asks
`spatial`. Nothing new in the engine.

- Click selects; ctrl-click adds, matching the explorer's existing modifier.
- Drag on empty space is a box select, which is `RaycastAll`'s sibling — an
  overlap query against the frustum slab, not N raycasts.
- Hover highlights, selection draws an outline. Both are overlay work in the same
  draw list as §4.2, with the same last-frame matrix.
- The explorer scrolls to what the viewport selected. Selection is one set with
  two views of it, which it already is.

**Gizmos record, they do not write.** A drag accumulates a delta in `Editor` and
commits one `PendingTransform` on release — one command in the log per drag, not
one per frame, or the undo stack fills with a hundred entries describing one
motion. Move, rotate and scale; world and local space; grid snap and angle snap
with their steps in the toolbar.

**Camera.** Focus-selection on `F` framing the selection's bounds, frame-all,
orthographic front/side/top, and the speed control moved to the toolbar. These
are five new `Action` entries and therefore five operator-table rows, which is
§4.8's registry earning its place immediately.

### 4.7 · The script editor

Monospace and a line gutter, which per §3.3 needs no new file and no licence
decision. Find and replace. Error markers that jump to a line, sharing the jump
that §4.4 gives Output.

**Highlighting uses Luau's own lexer rather than a regex.** `mono.vendor/luau` is
pinned to the same commit as `luau-lsp`'s copy — `docs/DEFERRED.md` records that
`just luau-lsp` refuses to build when the two `HEAD`s differ, precisely so an
author never reads diagnostics from a language the engine does not run. A
hand-written highlighter would be a third opinion on what Luau's syntax is, and
it would drift silently. The one honest complication: `script::LanguageOf` picks
per file and the studio can hold a JavaScript file it will not run, so the
highlighter is selected per tab from the same function and a file with no lexer
renders plain.

### 4.8 · The operator table, and what it makes possible

`Keybinds::Action` generalises into the operator record of §3.2 — name,
description, scope, poll, execute — and gains the entries §4.6 introduces.

- **Command palette** on `Ctrl+Shift+P`, walking the registry, filtered with the
  existing `FuzzyMatch`, showing each operator's binding beside it and greying
  what polls unavailable *with the reason*.
- **Menus stop hand-writing their enable conditions.** Each menu item asks its
  operator's poll instead, so `!Selection.empty()` is written once.
- **The MCP surface grows from the same table** rather than from a second list in
  `control/Tools.cpp`. That is `MCP.md` §3's whole argument, and it is what would
  eventually let an agent drive the editor rather than only the universe.

**Explorer** gains shift range-select alongside the ctrl-toggle it has, class
icons, sort, and a filter by class beside the existing name filter.

**Properties** gains a reference picker — the `PropertyType::Reference` that
today shows a name and cannot be changed — multi-instance editing showing a mixed
marker where selected instances disagree, and revert-to-default. The reference
picker is the modal over the tree that `AGENTS.md` names; it is cheap now that
the explorer's tree drawing is a function the modal can call.

## 5 · Order of work, and why this order

| # | Work | Why here |
|---|---|---|
| 1 | §4.1 status bar, modals | Smallest, and the status bar is the readout everything after this is judged by. Fixing it first means the fps and draw-call numbers are visible while the rest is built |
| 2 | §4.5 undo | Per §3.1, cheapest before §4.6 and §4.8 add mutations. Every later item registers commands rather than being retrofitted with them |
| 3 | §4.8 operator table | §4.6 adds five camera actions and four tool modes. They should land *as* operators, not be converted into them afterwards |
| 4 | §4.2 grid and axes | Establishes the overlay path and the retained view-projection that §4.6 needs. Small, visible, and the projection trap is easier to find with a grid than with a gizmo |
| 5 | §4.6 picking, gizmos, camera | The largest item, and it consumes 2, 3 and 4 |
| 6 | §4.3 layout and toolbar | After the tool modes exist, so the toolbar is arranged around real controls. **The one `DOCKSPACE` bump lives here** |
| 7 | §4.4 files and output, §4.7 script editor | Independent of everything above; last because they are the least blocking |

Items 1–2, 4 and 6–7 are each verifiable by running the studio and looking at it.
Item 3 is verifiable by the palette listing what the menus list. Item 5 is the
one that wants a scene in front of it.

| 4.3 layout | **not done, deliberately** | The default arrangement is unchanged, so `DOCKSPACE` stays at `v5`. See below |

**Why the layout was left alone.** The plan said to make Viewport 2 a tab beside
Viewport rather than a split. `BuildDefaultLayout`'s own comment says why that
cannot be done: docking both viewports into one node makes the second a
*background* window, so `ImGui::Begin` returns false, the panel drops its render
target and the second view is simply never drawn. The plan was wrong and the code
already carried the answer.

What remains of §4.3 is proportions and tab order, which is taste — and changing
it costs a `DOCKSPACE` bump, which `AGENTS.md` says costs everybody their saved
layout. Not worth spending on a guess. The toolbar half of §4.3 landed.

**Why the script editor stops where it does.** `CodeField` is
`ImGui::InputTextMultiline`, and the three things left all need something imgui
does not expose:

- **A line-number gutter** has to scroll in step with the field, and the field's
  scroll lives in its own child window — reachable only through
  `imgui_internal.h` by finding that window by name.
- **Find Next** has to move the caret, which means writing to
  `ImGuiInputTextState`.
- **Syntax highlighting** cannot be done to `InputTextMultiline` at all. The
  widget draws its own text in one colour; per-token colouring means replacing
  its rendering, which is writing a code-editor widget — a component on the scale
  of `ImGuiColorTextEdit`, not an increment on this one.

All three are the same decision rather than three: **either the script editor
keeps imgui's text widget and stops here, or it grows its own.** Growing its own
is a real piece of work and it is the wrong time to start it, because v0.8's
whole argument is that the studio's panels move to the engine's own UI — and a
hand-written imgui code editor would be the largest thing to throw away when they
do. `mono.studio/AGENTS.md`'s deferred list should now read "no syntax
highlighting", with the font half struck out.

### What v0.7 does not get

Said plainly rather than discovered later: no asset browser (nothing to browse
until meshes and textures import), no inspectors (§6), no live collaboration, no
animation or audio panels, and no engine-drawn UI. The editor at the end of v0.7
is Dear ImGui throughout, deliberately.

## 6 · v0.8 — what waits, and what it waits on

v0.8's own roadmap section is about the gui tree, and it ends with **"the
studio's own panels, authored in TypeScript — this is the point of all of it and
it is the *last* step, not the first."** Everything here sits before that
sentence and is therefore still imgui.

### 6.1 · The three inspectors

`MCP.md` §1 makes the argument that decides these: **build the introspection
contract per layer, and expose it per artefact.** The resource viewer reads L0
and L8, the network inspector reads L11, an ECS inspector reads L3 — and all
three have to exist for the studio regardless. Written as panels over a per-layer
query contract, the MCP servers are a second consumer of the same queries rather
than a second implementation. Written as MCP tools first, the panels reimplement
them.

- **ECS Inspector** (L3) — archetypes, columns, entity counts per archetype,
  component memory. Backs `world_list` and `world_tree`, which today answer from
  their own traversal.
- **Network Inspector** (L11) — links, bandwidth, per-assembly ownership, and the
  per-component `ChangeDetection` table. `docs/DEFERRED.md` records that table
  existing in three programs with nothing comparing them, and that the failure
  mode is a value that crosses in the studio and not on a server. **A panel that
  shows what this program's table says is the cheapest thing that would have
  caught it.**
- **Resource Viewer** (L0/L8) — allocations, arena occupancy, asset residency.

### 6.2 · The artefact panels

`MCP.md` groups `replay` and `render` together because both back onto a recorded
artefact rather than a live process, both seek within it, and **both answer their
real question by diffing two of them**. The panels inherit that shape.

- **Test Runner** over `mono.tools/testrunner` — run, filter, failures,
  jump-to-source through §4.4's jump.
- **Replay / Timeline** — a tick scrubber and a two-run diff. `DEFERRED.md`
  records that world state is already fingerprinted per tick for desync detection
  and that L11 already records ticks for rollback, so "where did these two runs
  first diverge" is a comparison over data that exists rather than a new
  recording path. This is the highest ratio of value to new code in the whole
  document.
- **Frame Capture** — pass list, per-pass timing, draw list, and a diff against a
  saved capture. `--profile-snapshot` already writes one.

### 6.3 · Asset Browser

Content tree, thumbnails, usage and cost. **Gated, honestly, on v0.8's mesh and
texture import** — the roadmap items for importing, baking and the import node
pipeline. Built before those it is a shell listing nothing, which is the
API-with-no-caller this repository refuses everywhere else.

### 6.4 · Docs panel

A searchable view of the surface manifest, with insert-snippet. `MCP.md` §3 notes
the manifest already emits C++ registration tables, `.d.luau`, `.d.ts` and the
reference pages from one declaration, and that MCP descriptors are a fifth output
of the same generator. **This panel is a sixth**, and it inherits the property
that it cannot drift from the engine.

## What would make this plan wrong

Two things, named so they are recognisable:

**If the `Pending*` seam turns out not to cover everything.** §3.1's whole
argument is that every mutation passes through two appliers. If a write is found
that reaches a store from somewhere else, the command log has a hole and §5's
ordering is wrong rather than merely inconvenient — undo would need that write
routed before it could be recorded. The check is mechanical and should be run
before item 2 starts: every `Universe::Enter` call site in `mono.studio` that
writes, compared against the appliers.

**If the retained view-projection of §4.2 is not enough to stop the swim.** The
claim is that projecting the overlay with the matrix that produced the displayed
texture aligns it exactly. If the renderer's reported sub-rect and the panel's
image rect disagree by even a pixel under display scaling, the grid will sit
slightly off and picking will be slightly wrong — and picking being *slightly*
wrong is far harder to notice than being obviously wrong. Item 4 exists before
item 5 so that a grid, which is forgiving, finds this before a gizmo, which is
not.
